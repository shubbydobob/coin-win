# 구현 로드맵

각 Phase는 **배포 가능한 상태**로 끝난다. 미완성으로 다음 Phase에 넘어가지 않는다.

> 현재 Phase: **8 — 계획된 Phase 가 전부 끝났다.**
> § 11 의 완료 조건 일곱 개를 모두 통과했고 브라우저 실측까지 마쳤다.
> 이후의 작업은 Phase 가 아니라 개별 변경으로 다룬다 — § "Phase 이후" 에 한 항목씩 적는다.

---

## Phase 0 — 기반 (0.5주)

- Gradle, Java 21, Spring Boot 3.x
- Checkstyle / SpotBugs / JaCoCo / ArchUnit + CI 연결
- **ArchUnit 규칙을 코드보다 먼저 작성** (architecture.md의 6개 규칙 전부)
- 각 규칙마다 일부러 위반하는 샘플로 실패를 먼저 확인
- springdoc-openapi 설정
- `common/domain` 값 객체 4종 + 테스트

**완료 조건:** 빈 프로젝트에서 `.\gradlew.bat check` 통과.

6개 규칙 각각에 대해 위반 픽스처(`src/archFixture/java/archfixture/r1`~`r6`)가 존재하고, `ArchitectureRulesViolationTest`가 각 규칙이 해당 픽스처에서 `AssertionError`를 던지는 것을 단언한다. 특히 규칙 4·5의 위반 픽스처가 규칙을 실제로 발동시키는지 테스트 출력으로 확인한다.

> 코드를 임시로 깨뜨렸다 원복하는 방식이 아니라 픽스처를 상주시키는 이유: 임시 파괴는 확인이 1회성이고 원복 실패 위험만 추가된다. 픽스처는 매 빌드마다 재검증되고, "통과하는 것처럼 보이지만 아무것도 매칭하지 않는 규칙"까지 잡아낸다.

## Phase 1 — 포지션 계산 (1주)

- `position/domain` 전체 + 테스트
- REST API + Swagger
- **DB 없음. 순수 계산만.**

**완료 조건:** 50% 분할 시나리오에서 1차 체결 상태와 전량 체결 상태의 평단·청산가·최대손실이 각각 정확히 산출. 도메인 커버리지 90% 이상.

## Phase 2 — 복리 / 몬테카를로 (0.5주)

- `projection/domain`
- 초기자본·승률·손익비·거래빈도 → 자산 곡선
- 동일 조건 N회 시뮬레이션 → 결과 분포

**완료 조건:** 같은 기댓값에서도 경로에 따라 결과가 갈리는 것이 수치로 나온다.

## Phase 3 — 시장 데이터 (1.5주)

- `market/application/port/out` 포트를 **어댑터보다 먼저** 정의
- 어댑터 3종: binance / persistence / memory
- 캔들 저장 + Testcontainers 통합 테스트
- 펀딩비 / OI / 롱숏비율 API
- `MaintenanceMarginPolicy`를 `leverageBracket` 기반 구현체로 교체
- **`market` 패키지 생성 후 `ArchitectureRules`에서 규칙 4·6의 `allowEmptyShould(true)` 제거.** 대상 패키지가 없어 매칭 0건이던 규칙이 이제 실제로 검사하므로, 플래그를 남겨 두면 규칙이 공허하게 통과해도 알 수 없다. (규칙 1·3은 Phase 0에서 제거 완료)

**완료 조건:** 캔들 증분 저장에 중복 없음. Phase 1 청산가가 거래소 실제값과 오차 범위 내 일치. **동일한 `LoadCandlesPort` 계약 테스트가 세 어댑터 모두 통과.**

> **Phase 3 에서 드러난 것 — `leverageBracket` 은 공개 엔드포인트가 아니다.**
> 서명 없이 부르면 401 이다. `scope.md` 전제상 API 키를 쓰지 않으므로 구간표는 커밋된
> 스냅샷에서 읽고 갱신은 파일 교체로 한다. 근거는 `docs/adr/013` 이 아니라 위 조사 결과이며,
> 스냅샷 손상은 `LeverageBrackets` 의 연속성 검사가 잡는다.
>
> 청산가는 근사식을 버리고 거래소 정확식으로 교체했다(`docs/adr/012`). 완료 조건의
> "거래소 실제값" 은 계좌 권한 없이 얻을 수 없으므로, *바이낸스 공개 공식 + 공개 구간표로
> 손으로 푼 값*을 기준으로 삼고 오차 허용치 없이 센트 단위 일치를 요구한다.
>
> 저장은 JPA 가 아니라 `JdbcTemplate` + `ON CONFLICT` 다(`docs/adr/011`). JPA 는 Phase 5 에
> QueryDSL 과 함께 들어온다.

## Phase 4 — 지표 (1주)

- `indicator/domain` 일목 · 볼린저
- golden test로 정확성 고정

**완료 조건:** 트레이딩뷰 값과 일치.

> **Phase 4 에서 드러난 것 — golden test 가 전부 초록인데 구름이 한 칸 밀려 있었다.**
>
> 트레이딩뷰 값은 코드로 가져올 수 없다. 그래서 golden test 의 기준값은 *닫힌 식이 나오는
> 합성 캔들*(등차수열의 모집단 분산, 단조 증가 캔들의 이동 최대·최소)과 *극값이 구간 중간에
> 오는 비단조 13봉*에서 얻었다(`docs/adr/015`). 그런데 이 테스트들이 증명하는 것은 "구현이
> **명시된 공식**을 정확히 따른다" 까지다. 공식 해석 자체가 어긋나면 전부 통과하면서 값이
>틀린다. **실제로 일목 변위가 그 지점이었다.**
>
> 확정은 차트 대조가 아니라 **트레이딩뷰가 배포하는 Pine 소스 원문**으로 했다
> (`pine-facade.tradingview.com/pine-facade/get/STD;Ichimoku%1Cloud/34.0`). 선행스팬 플롯이
> `offset = displacement - 1` 이라 변위 26 은 실제로 **25봉**을 민다. 값 몇 개를 눈으로 맞대는
> 것보다 강한 증거다 — 특정 시점이 아니라 모든 입력에 대해 성립하기 때문이다. 볼린저도 같은
> 방법으로 확인했고 그쪽은 처음부터 일치했다. 원문은 `docs/adr/014`·`015` 에 인용해 두었다.
>
> 남은 것은 **차트에 렌더링된 수치와의 대조 한 번**이다. 소스가 같으므로 값도 같지만 그것은
> 연역이지 관측이 아니다. `.\gradlew.bat crossCheck` 가 실제 캔들의 우리 값을 찍는다.
>
> 명세와 달라진 것 셋(공유 `PriceBand`·`Optional` 후행스팬·설정 변위)은
> `.claude/skills/domain-model/SKILL.md` 지표 절에 반영했다.

## Phase 5 — 매매 기록 (1주)

- 포트 정의 → 인메모리 어댑터 → JPA 어댑터 순
- 계획 저장 → 체결 → 청산 기록
- 집계: 계획 준수 여부별 손익 분리, 반사실 손실, 거래 간격
- 동적 조회는 QueryDSL (`io.github.openfeign.querydsl:7.6` — 원본 `com.querydsl`은 2024-11 이후 미유지)
- **`journal` 패키지 생성 후 규칙 4·6이 `journal.application` / `journal.adapter.out`까지 실제로 검사하는지 확인.** `allowEmptyShould`는 Phase 3에서 이미 제거됐으므로 여기서 새로 뗄 플래그는 없다. 확인 방법은 `journal` 위반 픽스처를 `archfixture`에 추가하는 것이다.

**완료 조건:** 실제 매매 1건이 처음부터 끝까지 기록되고 집계에 반영. 애플리케이션 서비스 테스트가 **DB 없이 인메모리 어댑터만으로** 전부 통과.

> **Phase 5 에서 드러난 것 — 상태를 타입으로 나눈 것이 가장 값을 했다.**
>
> 명세의 `TradeRecord` 는 청산된 거래를 전제한 단일 record 였다. 그런데 이 모듈은 "계획 저장 →
> 체결 → 청산" 세 번을 쓴다. `Optional<Money> realizedPnl` 로 두면 미청산 거래를 걸러 내는
> 분기가 집계·조회·표시에 흩어지고, 그중 한 곳에서 `orElse(ZERO)` 를 쓰는 순간 미청산 거래가
> 손익 0 인 거래로 집계에 섞인다. **`sealed interface Trade` + `PlannedTrade` / `OpenTrade` /
> `ClosedTrade` 로 나눴고, `JournalSummary.of` 가 `List<ClosedTrade>` 만 받는다** — 필터를
> 빠뜨리면 컴파일이 안 된다. 서비스의 상태 전이 검사도 sealed 위의 `switch` 라 상태가 늘면
> 컴파일 오류로 알려 준다.
>
> **파생값은 저장하지 않는다.** 진입 시각·평단·손익은 전부 체결 내역에서 다시 계산한다. 그
> 대가로 진입 시각 정렬을 SQL 로 할 수 없어 자바에서 정렬하는데(`docs/adr/016` 한계),
> 두 번째 사본이 원본과 갈라지는 것보다 낫다고 봤다. 1인 사용자 규모에서 성립하는 선택이다.
>
> **손익은 입력받지 않고 계산한다.** 거래소 화면의 숫자를 그대로 받으면 체결 내역과 손익이
> 어긋나 있어도 알 방법이 없다. 받는 것은 재현할 수 없는 것 — 수수료와 펀딩비 — 뿐이다.
> 반사실 손실은 같은 공식에 청산가 대신 손절가를 넣은 것이라 실제와 나란히 비교된다.
> 펀딩비를 반사실에서 빼지 않는 이유는 **오래 들고 있어서 낸 펀딩비가 어긴 대가의 일부**이기
> 때문이다.
>
> **JPA 는 실제로 값을 했다**(`docs/adr/016`). ADR 011 이 "journal 은 판단이 다를 수 있다" 고
> 남겨 둔 자리다. 자식 목록 둘을 거느린 덩어리이고 조회 조건이 다섯 개라 그렇다. Boot 4.1 /
> Hibernate 7.4.5 / QueryDSL 7.6(openfeign 포크) 호환은 **스파이크로 먼저 확인하고** 들어갔다.
>
> **`MarketContext` 의 지지·저항은 구조화하지 않았다.** 저항대의 코드 정의가 Phase 6 의 첫
> 작업이므로, 지금 스키마를 박으면 정의가 확정되는 순간 이미 쌓인 기록을 못 쓰게 된다.
> 구조화한 것은 지표(`BandPosition`)뿐이고 근거는 자유 텍스트다. 그 참조가
> `journal → indicator.domain` 의존을 만들었다 — `docs/adr/017`.
>
> 규칙 4·6 이 `journal` 까지 실제로 검사하는지는 `archfixture.r4j` / `r6j` 가 증명한다.
> 규칙 4 는 모듈 이름을 손으로 열거하므로 모듈마다 픽스처가 필요하다.

## Phase 6 — 백테스트 (2주+)

- 캔들은 `LoadCandlesPort`로만 읽는다
- 지지·저항 기반 양방향 전략을 코드로 정의
- **분할 진입 지원** (차별점)
- 수수료·슬리피지 반영
- 결과: 승률, 손익비, MDD, 자산 곡선
- **`backtest` 패키지 생성 후 규칙 5의 `allowEmptyShould(true)` 제거. 이것이 마지막 플래그다.** 제거 후 `ArchitectureRules`에 `allowEmptyShould`가 하나도 남지 않아야 한다.

**주의:** 이 Phase에서 "저항대"를 코드로 정의해야 한다. 정의가 애매하면 백테스트가 성립하지 않는다. 시작 전 `AskUserQuestion`으로 인터뷰해서 `SPEC.md`를 먼저 뽑고, 새 세션에서 구현한다.

**완료 조건:** 동일 파라미터 재실행 시 결과 완전 동일. `backtest`에 바이낸스 관련 코드가 한 줄도 없다.

> **Phase 6 에서 드러난 것 — 명세가 틀린 것을 두 번 잡았고, 둘 다 코드가 아니라 대조가 잡았다.**
>
> 인터뷰로 12개 논점을 닫아 `docs/spec/phase6-backtest.md` 를 먼저 썼다. 그런데 그 명세가
> 두 군데 틀려 있었다.
>
> 하나는 **ATR 워밍업**이다. 초안은 "첫 값이 index `period`" 라고 적었는데 실제로는
> `period − 1` 이다 — `ta.tr(true)` 가 첫 봉에도 값을 낸다. **트레이딩뷰 Pine 소스 원문
> 대조가 잡았다**(`docs/adr/018` 아니라 ATR 절). 한 칸 밀린 구현도 그럴듯한 숫자를 내므로
> 값을 눈으로 봐서는 알 수 없다. Phase 4 의 일목 변위와 같은 종류다.
>
> 다른 하나는 **"롱·숏 후보가 동시에 서면 둘 다 버린다"** 였다. 가격은 거의 항상 어떤 지지
> 위이면서 어떤 저항 아래이므로 그 규칙은 모든 거래를 없앤다. 구현하다 발견했다. 근단이
> 가까운 쪽 하나만 무장하는 것으로 고쳤다.
>
> **명세를 먼저 쓴 것은 여전히 옳았다.** 두 오류 모두 "이 문장이 코드에서 무엇이 되는가" 를
> 물었기 때문에 드러났다. 명세가 없었으면 그냥 그렇게 구현하고 넘어갔을 것이다.
>
> **역할을 파생값으로 둔 것이 가장 값을 했다.** 대의 지지/저항 판정을 상태로 저장하지 않고
> `roleAt(종가)` 로 매번 다시 묻는다. 돌파 플래그를 뒤집는 방식이면 "언제 뚫린 것으로
> 보는가" 라는 두 번째 정의가 필요하고 그 상태가 재실행 사이에 남아 결정론이 깨진다.
> 역할 전환이 공짜로 따라왔다.
>
> **룩어헤드는 케이스가 아니라 성질로 검증한다.** 뒤에서 K봉을 떼고 돌려 겹치는 구간의 거래가
> 같은지 본다. 피벗 확정 지연·후행스팬·인덱스 밀림을 원인과 무관하게 한 테스트가 잡는다.
> 테스트 픽스처에서도 하나 배웠다 — 톱니의 전환점을 단조로 흘리면 새 저점이 언제나 이전보다
> 높아 **가격이 과거 지지대로 되돌아오지 않는다.** 신호는 154건 서는데 체결이 0건이었다.
>
> **`journal` · `projection` 의 어휘를 그대로 쓴다**(`docs/adr/018`). 백테스트 거래도
> `ClosedTrade` 이므로 `JournalSummary` 를 그대로 씌울 수 있고, 검증한 전략과 실제 기록이
> 같은 기준으로 비교된다. 따로 정의하면 "0 원은 승리가 아니다" 같은 규칙이 두 곳에서 갈라져
> 비교 자체가 무의미해진다.
>
> **실제 캔들에서 이 전략은 돈을 잃는다.** BTCUSDT 4시간봉 1,500개(2025-12-14 ~ 2026-08-21),
> 파라미터 18조합 중 **15조합의 손익비가 1 미만**이었다. `.\gradlew.bat crossCheck` 가 그 표를
> 찍는다.
>
> | 조합 (피벗/군집/버퍼) | 거래 | 승률 | 손익비 | 순손익 | 최대낙폭 |
> |---|---|---|---|---|---|
> | 5 / 0.3 / 0.5 | 119 | 26.9% | 0.54 | −717 | **89.8%** |
> | 5 / 0.5 / 1.0 (기본) | 24 | 33.3% | 0.70 | −80 | 12.5% |
> | 5 / 1.0 / 0.5 | 33 | 48.5% | 1.33 | +98 | 22.0% |
> | 5 / 0.5 / 1.0 + 지표 필터 | 12 | 41.7% | 1.14 | +17 | 6.5% |
>
> **이것이 Phase 6 의 산출물이다.** 백테스터를 만드는 것이 목적이었고, 그 백테스터가 낸 첫
> 대답이 "이 규칙에는 엣지가 없다" 인 것은 실패가 아니라 도구가 작동한다는 증거다. 실계좌에
> 800 USDT 를 넣기 전에 알았다는 것이 이 Phase 전체의 값이다.
>
> 구조적으로 읽히는 것 셋:
>
> - **손절 버퍼 0.5 ATR 은 너무 좁다.** 0.5 인 조합의 낙폭이 32~90% 인데 1.0 으로 늘리면
>   전부 8~29% 로 떨어진다. 대가 진짜로 뚫린 것이 아니라 꼬리에 스친 것을 손절로 세고 있다.
> - **피벗 8봉은 일관되게 나쁘다.** 대가 너무 적게 잡혀 남은 대가 실제 반응 지점이 아니다.
> - **지표 필터가 유일하게 일관된 개선이다.** 거래를 24 → 12 로 절반 줄이면서 손익비를
>   0.70 → 1.14 로 올린다. 다만 **12건은 통계가 아니다.** 이 숫자로 필터가 값을 한다고
>   결론 내리면 안 된다.
>
> **기본값을 바꾸지 않았다.** 이 표의 최고 조합(5 / 1.0 / 0.5, 손익비 1.33)을
> `ZoneSettings.standard()` 로 박는 것이 과최적화의 정의 그 자체다. 33건 표본에서 나온 숫자이고
> 인접 조합(5 / 1.0 / 1.0)은 손익비 0.99 로 뒤집힌다 — **한 칸 바꿔서 결과가 뒤집히는 파라미터는
> 전략이 아니라 잡음을 고르고 있다.** 기본값은 5 / 0.5 / 2 / 14 로 둔다.
>
> **다음에 할 일은 파라미터 튜닝이 아니다.** 진입 규칙 자체를 다시 봐야 한다. 후보는 셋이다 —
> 구간 밖(walk-forward) 검증, 다른 주기(1시간·일봉) 대조, 그리고 "대에 닿으면 되돌아온다" 는
> 전제 자체의 재검토. 어느 쪽이든 **표본 수를 먼저 확보**하지 않으면 같은 함정에 빠진다.
>
> **후속 (2026-08-23) — 셋을 전부 돌렸고 답이 같았다. `docs/adr/021` 을 본다.**
> 7년 이력에서 18조합 전부 손익비 1 미만, 워크포워드 5폴드 전부 검증 실패, 세 주기 전부 실패.
> 위 표의 "최고 조합" 5 / 1.0 / 0.5 는 7년에서 1.33 이 아니라 **0.80** 이다.

## Phase 7 — Spring AI (1.5주)

범위는 scope.md 참조. 자연어 → 매매 계획 파싱 / 백테스트 결과 요약 / 매매 기록 RAG.

**완료 조건:** `OPENAI_API_KEY` 없이 `.\gradlew.bat check` 통과. 실제 매매 1건이 청산 →
자동 색인 → 질의에 잡히는 것이 통합 테스트로 확인. `ai` 밖의 어떤 모듈도 `ai` 를 참조하지
않는다(요약을 부르는 `backtest.api` 하나만 예외이며 역방향은 없다).

> **Phase 7 에서 드러난 것 — 검증을 테스트에만 두면 검증하지 않은 것과 같다.**
>
> ADR 005 는 "요약은 원본 수치와 대조할 수 있다" 를 근거로 요약을 허용했다. 그 대조를
> 테스트에만 두면 **실제 응답은 검증되지 않은 채 나간다.** 그래서 세 기능의 출력 규칙을
> 전부 도메인 생성자에 뒀다(`docs/adr/019`). 빈 칸이 있는 계획, 원본에 없는 수를 쓴 요약,
> 검색되지 않은 거래를 인용한 답은 **존재할 수 없다.**
>
> 규칙이 느슨해진 곳이 둘이다 — 반올림(12.4567 → 12.5)과 1000 미만 정수("두 가지").
> 막으면 읽을 수 있는 문장이 나오지 않는다. 남은 구멍은 "약 6만" 같은 단위 표기다.
>
> **명세가 또 두 군데 틀렸고 둘 다 코드가 아니라 제약이 잡았다.**
>
> 하나는 **총수량**이다. 초안에 수량 칸을 두려 했는데, 이 프로젝트에서 수량은 입력이 아니라
> 손절가가 결정하는 출력이다. 두면 모델이 채운 숫자가 리스크 사이징을 건너뛴다.
>
> 다른 하나는 **요약의 자리**다. `ai` 가 백테스트를 돌려 요약하게 두면 `ai ↔ backtest`
> 순환이 되고 ArchUnit 규칙 3 이 빌드를 세운다. `SummaryFacts` 를 백테스트와 무관한
> "숫자 딸린 사실 묶음" 으로 정의하고 방향을 한쪽으로 냈다 — **제약이 더 나은 모양을
> 만들었다.** 요약이 백테스트 전용이 아니게 됐다.
>
> **스텁과 실제 모델이 답하는 질문이 다르다.** 기본 `test` 는 "모델이 이렇게 답하면 우리는
> 이렇게 한다" 만 증명한다. "모델이 이 문장에 이렇게 답한다" 는 결정론적이지 않으므로
> `.\gradlew.bat liveAi` 로 걷어냈다 — Phase 4 `crossCheck` 와 같은 형태다. 초안에 12개
> 케이스를 한 표로 적었던 것은 그 둘을 섞은 것이었다.
>
> **키 없이 도는 것이 설정 한 줄로 되지 않았다.** OpenAI 자동 구성은 키가 없어도 음성·이미지
> 모델 빈을 만들려 하고 SDK 가 빈 생성 단계에서 던진다. 환경 후처리기가 그 자리이고,
> 그 값은 `addLast` 여야 한다 — 기본값이지 강제가 아니다.
>
> **RAG 는 순서를 미리 계산해 두지 않으면 성립하지 않는다.** ADR 005 가 예로 든 "손실 직후
> 진입한 거래" 는 의미 검색으로 찾을 수 없다. 유사도는 문장이 닮은 정도만 보고 "직후" 는
> 순서에서만 나온다. 색인은 항상 시간순 전체 목록 위에서 하고, `afterLoss` 를 문장과
> 메타데이터 양쪽에 박는다. **첫 거래에는 그 키가 아예 없다** — 없는 것을 `false` 로 적으면
> "손실 직후가 아니었다" 는 거짓말이 되고 그것은 조건 검색에 그대로 걸린다.
>
> **가짜 임베딩이 통합 테스트를 키에서 풀어 줬다.** 결정론적 해시 임베딩을 물리면 pgvector
> 어댑터가 **키 없이 진짜 PostgreSQL 위에서** 돈다. V3 마이그레이션·차원 일치·덮어쓰기·비우기
> ·topK 가 전부 검증되고, 검증되지 않는 것은 임베딩 품질 하나뿐이다 — 그것은 어차피 어떤
> 자동 테스트로도 고정할 수 없다.
>
> **그리고 하나를 잡았다 — `spring.flyway.enabled: true` 가 Phase 3 이후로 아무 일도 하고
> 있지 않았다.** Boot 4 는 자동 구성을 기술별 모듈로 쪼갰고 `flyway-core` 만으로는 배선이
> 붙지 않는다. 통합 테스트가 전부 Flyway 를 손으로 돌려서 **앱 기동 경로가 한 번도 검증된
> 적이 없었다.** Phase 7 이 처음으로 컨텍스트를 띄운 채 DB 를 쓰면서 드러났다.
> 교훈은 Flyway 가 아니다 — **손으로 우회한 배선은 검증되지 않는다.**

## Phase 8 — 프론트엔드 (2주)

React + TypeScript + Vite + Recharts. 화면 다섯 개, 게이트 하나(`.\gradlew.bat check`).

**완료 조건:** `docs/spec/phase8-frontend.md` § 11 의 일곱 개를 **전부 통과했다.** 마지막 둘은
브라우저로 실측했다 — 매매 1건(계획 → 체결 → 청산 → 집계 15.41)과 백테스트 한 번(바이낸스
캔들 1,272개 동기화 → 거래 23건 · 손익비 0.73).

> **Phase 8 에서 드러난 것 — 아무도 읽지 않던 문서는 코드와 갈라져 있었다.**
>
> 명세가 **일곱 군데** 틀렸다. Phase 6 과 7 이 각각 두 건이었으니 가장 많다. 이유는 하나다 —
> **프론트가 백엔드 계약을 처음으로 소비하는 쪽**이고, 그전까지 OpenAPI 문서를 읽는 사람이
> 없었다. 스키마는 Phase 0 부터 있었지만 그것이 사실인지 검사하는 것이 아무것도 없었다.
>
> 스키마가 거짓말을 하던 곳이 셋이다.
>
> - **응답 필드가 전부 optional 이었다.** springdoc 이 `required` 를 내지 않는다. 그러면
>   *항상 있는 값*과 *진짜 null 인 값*이 구별되지 않고, 그것이 "손익비 0 과 손익비를 말할 수
>   없음은 다른 사실" 을 타입 수준에서 지운다. 커스터마이저 하나로 고쳤는데, `nullable` 을
>   붙여도 **`$ref` 필드는 여전히 거짓말을 했다** — swagger-core 가 `$ref` 옆에 형제 키로
>   붙이고 생성기는 그것을 무시한다.
> - **오류 응답에 성공 DTO 가 씌워져 있었다.** "계획 저장이 422 일 때 `TradeResponse` 가
>   온다" 고 적혀 있었고 `ProblemDetail` 은 컴포넌트에 아예 없었다. 그 김에 **19개 오퍼레이션
>   중 14개가 성공 응답을 선언하지 않고 있는 것**도 드러났다 — `@ApiResponses` 에 오류만
>   적으면 springdoc 이 기본 200 을 지운다. 생성된 타입에서 응답이 `never` 가 되어 그
>   엔드포인트를 부르는 코드를 **아예 쓸 수 없었다.**
> - **조회 조건이 와이어에 없는 모양이었다.** 스프링은 레코드를 개별 질의 파라미터로
>   바인딩하는데 문서는 `params` 라는 객체 하나로 적고 있었다. 그 문서를 믿은 소비자는 있지도
>   않은 `?params=…` 를 보내게 된다.
>
> 셋 다 **소비자가 없어서 아무도 몰랐다.** 고친 뒤에는 각각 규칙 하나와 테스트 하나가 남았고,
> 그 규칙들은 필드나 엔드포인트 목록을 갖지 않는다 — "이름이 `Response` 로 끝나면", "2xx 가
> 아니면", "질의 파라미터는 객체를 가리키지 않는다".
>
> **명세를 먼저 쓴 것은 이번에도 옳았다.** 일곱 건 모두 "이 문장이 코드에서 무엇이 되는가" 를
> 물었을 때 드러났고, 다섯 건은 **검증하려던 문장이 아니라 그 문장이 전제하던 다른 문장**이
> 틀린 것이었다. Phase 6·7 과 같은 모양이다.
>
> **규칙을 화면 하나 뒤에 정한 것도 값을 했다.** § 3.1 의 금지 목록에 `toFixed` 만 있었는데
> `format/` 이 실제로 쓰는 것은 `Intl.NumberFormat` 이었다 — 규칙을 쓸 때 상상한 도구와 코드가
> 쓰는 도구가 달랐고, 그대로 뒀으면 **가장 흔한 반올림 경로를 규칙이 그냥 통과시킨다.**
>
> **테스트가 거짓 초록을 하나 숨기고 있었다.** `"계획 익절"` 이 표에도 있고 필터 `<option>`
> 에도 있어서 `findByText` 가 옵션을 먼저 잡고 **데이터를 기다리지 않은 채** 통과했다. 다른
> 테스트가 실패하면서 드러났다. 역할(`cell`/`rowheader`)로 가리키게 고쳤다.
>
> 판단 하나는 ADR 로 남겼다 — `docs/adr/020`, 프론트는 숫자를 만들지 않는다. 규칙이 실제로
> 유혹받은 자리 넷을 함께 적었다.
>
> **그리고 마지막에, 사람이 한 번 훑는 자리가 가장 큰 것을 잡았다.**
>
> 브라우저에서 백테스트를 처음 돌리자 화면이 죽었다 — `Cannot read properties of undefined`.
> **DTO 두 개의 단순명이 같았다**(`backtest` 와 `journal` 의 `TradeResponse`). springdoc 은
> 컴포넌트를 단순명으로 키잉하므로 하나가 다른 하나를 **조용히 덮었고**, 스키마는 백테스트
> 거래가 계획·상태·결과를 가진 매매 기록이라고 말하고 있었다.
>
> 이것이 § 5.4 가 경고한 "타입이 있다고 단언하는데 실제로는 없다" 의 가장 심한 형태다.
> `tsc` 도 린트도 77개 테스트도 전부 초록이었다 — **MSW 픽스처가 그 거짓 타입으로 작성됐기
> 때문이다.** 자기 자신을 근거로 삼은 검증은 무엇도 증명하지 않는다. § 10.4 가 "스키마가
> 같아도 값이 다를 수 있다" 며 남겨 둔 구멍이 정확히 이것이었고, **그 구멍은 사람이 한 번
> 띄워 보는 것 말고는 막을 방법이 없었다.**
>
> 이름 충돌은 세 건 더 있었다. 전부 갈랐고 `SchemaNameCollisionTest` 가 매 빌드 막는다 —
> 이 검사는 스키마 문서가 아니라 **클래스**를 본다. 문서에는 살아남은 이름 하나만 남으므로
> 덮였다는 사실이 문서에서는 보이지 않는다.
>
> 같은 확인에서 `compose.yaml` 이 PG18 이미지로 **기동조차 못 하고 있는 것**도 드러났다.
> Phase 7 에서 이미지를 바꾸면서 볼륨 마운트 경로를 안 고쳤고, 통합 테스트는 Testcontainers
> 를 쓰므로 아무도 몰랐다. Phase 7 의 교훈이 그대로 반복됐다 — **손으로 우회한 배선은
> 검증되지 않는다.**

## Phase 이후 — 개별 변경

Phase 가 끝난 뒤의 작업은 여기에 한 항목씩 적는다. 번호를 붙이지 않는다 — 순서가 정해져

### 전략 재검증 (2026-08-23) — 완료

Phase 6 이 남긴 숙제였다. **셋을 전부 돌렸고 셋 다 같은 답이 나왔다.** 근거와 표 전체는
`docs/adr/021`.

- **표본 확보** — 8개월(1,500봉) → 상장 이후 전체(15,110봉). 늘리지 못할 이유가 없었다.
  어댑터는 처음부터 페이징하고 있었고 엔진은 봉 수에 거의 선형이다. `BARS = 1500` 이라는
  상수 하나가 8개월이었던 이유의 전부다.
- **7년 감도표** — 18조합 **전부** 손익비 1 미만. 그중 여섯은 계좌를 완전히 태웠다
  (순손익 −801~−811, 낙폭 100% 초과 = 파산 후 거래 중단).
- **구간 밖 검증** — anchored walk-forward 5폴드 **전부** 실패. 학습에서 1.00~1.14 이던
  조합이 검증에서 0.61~0.84 다. 방향이 한 번도 반대로 나오지 않았다.
- **주기 대조** — 1h / 4h / 1d 전부 1 미만. 주기가 길수록 덜 나쁜 것은 거래가 적어 비용을
  덜 낸다는 뜻이지 엣지가 아니다.

> **드러난 것 — 8개월 표는 틀린 것이 아니라 짧았다.**
>
> Phase 6 은 이미 옳게 판단했다. "최고 조합을 기본값으로 박지 않는다", "한 칸 바꿔서 결과가
> 뒤집히는 파라미터는 잡음을 고르고 있다". **그 판단이 옳았다는 것을 이번에 수치로 확인했다** —
> 1.33 이던 조합이 7년에서 0.80 이다. 판단은 맞았는데 근거는 8개월뿐이었고, 그 사이의 간격을
> 메우는 데 필요한 것은 새 아이디어가 아니라 상수 하나였다.
>
> **연도별로 부호가 뒤집히는데, 어느 해가 좋은 해인지는 그 해가 끝나야 안다.** 2022·2024·2025
> 는 손익비가 1 을 넘는다. 그래서 연도별 표만 보면 "최근에는 괜찮다" 고 읽고 싶어진다. 그런데
> 같은 데이터 위에서 **앞만 보고 골랐을 때** 2022 년부터 다섯 번 전부 졌다. 뒤를 알고 보는
> 표와 앞만 보고 고르는 절차는 다른 것을 측정한다 — 워크포워드가 존재하는 이유다.
>
> **구간을 갈라 다시 돌리고 싶어지는 것이 함정이다.** 폴드마다 캔들을 잘라 돌리면 지표
> 워밍업이 폴드마다 되살아나 각 폴드 앞부분의 거래가 통째로 사라진다(4시간봉 일목 워밍업만
> 77봉, 열이틀). 룩어헤드의 **반대편**이라 "정보를 덜 주니 안전하다" 고 읽히지만, 표본을
> 얇게 만드는 쪽으로 결과를 왜곡한다. 전체에서 한 번만 돌리고 결과를 진입 시각으로 가른다 —
> 엔진이 인과적이라 그 가르기가 성립한다. `TradeWindow` 에 그 이유가 적혀 있다.
>
> **감도표가 답하지 못하는 질문이 있다는 것이 이번의 구조적 소득이다.** 한 구간에서 18조합을
> 돌려 최고를 집는 것은 측정이 아니라 고르기이고, 고른 구간에서 좋은 것은 정의상 언제나 좋다.
> `WalkForwardFold` 는 그 구분을 타입으로 만든 것이다 — `choose` 는 학습 구간만 보고,
> 검증은 `outOfSampleOf` 로 따로 꺼낸다. 한 메서드가 둘 다 하면 그 구분이 다시 무너진다.
>
> **고정 구간으로 바꿨다.** 기존 `crossCheck` 는 `Instant.now()` 기준이라 표가 매일 달라진다 —
> 문서에 적어 둔 표가 다시는 재현되지 않는다는 뜻이다. 새 대조는 시작·끝을 상수로 박았다.
> 과거 캔들은 변하지 않으므로 같은 명령이 언제나 같은 표를 낸다.

**다음에 물어야 할 것은 파라미터가 아니라 전제다.** 승률 20~43% 와 손익비 1 미만이 함께
나온다는 것은, 되돌아오는 경우가 있더라도 뚫리는 경우의 손실이 그것을 덮는다는 뜻이다.
후보는 반전이 아니라 **돌파** 쪽이거나, 대를 진입 신호가 아니라 **청산·사이징의 근거로만**
쓰는 쪽이다. 어느 쪽이든 명세를 먼저 쓰고 같은 절차로 잰다.

### 거래소 포지션 대조 (2026-08-23) — 완료

새 모듈 `account`. 기록의 `OPEN` 거래와 거래소의 실제 포지션을 **나란히 놓고 어긋나면
드러낸다.** 명세는 `docs/spec/phase9-exchange-positions.md`.

- **대체가 아니라 대조다.** 거래소 값으로 덮어쓰면 "청산을 적지 않았다" · "앱 밖에서 열었다"
  · "물타기가 안 적혔다" 가 전부 사라진다. 화면은 언제나 맞는 것처럼 보이고 계획 준수율은
  조용히 틀린다.
- **서명 경로가 처음 생겼다.** Phase 3 이 401 을 만나고 스냅샷으로 우회한 자리다. 구간표는
  거의 변하지 않아 그 우회가 옳았고, 포지션은 매 순간 달라져 성립하지 않는다.
- **키 없이 `check` 통과하고 앱이 뜬다.** `/api/account/positions` 만 503 이고 화면은 필요한
  환경변수 이름을 말한다. 브라우저로 확인했다.

> **드러난 것 — 명세가 두 군데 틀렸고 둘 다 구현이 잡았다.**
>
> 하나는 **맞추는 키**다. 초안은 "심볼로 맞춘다" 였는데 **`OpenTrade` 에 심볼이 없다** —
> 1종목 전제라 기록이 종목을 적지 않는다. 방향으로 바꿨고 그게 더 나은 모양을 만들었다:
> 기록이 롱인데 거래소가 숏이면 **짝이 지어지지 않아 두 건으로 갈린다.** 심볼로 맞췄다면
> 한 줄로 합쳐지고 "방향이 뒤집혔다" 는 가장 심각한 사실이 수량 불일치처럼 보였을 것이다.
>
> 다른 하나는 **청산가**다. 바이낸스는 청산 지점을 말할 수 없을 때 `"0"` 을 준다. 0 원짜리
> 청산가로 담으면 화면이 "곧 청산된다" 로 읽는다. `Optional` 로 바꿨다 — **손익비에서 이미
> 정한 규칙과 같다**(말할 수 없는 것을 0 으로 적지 않는다).
>
> **게이트 둘이 제 일을 했다.** 스키마 낡음 검사가 걸렸고, "null 이 오는 응답 필드" 전수
> 목록이 걸렸다. 후자는 Phase 8 이 일부러 손으로 세게 해 둔 자리이고, 목록을 고치는 순간
> "이것은 정말 null 이 오는가" 를 한 번 묻게 된다. 실제로 그 질문이 값을 했다.
>
> **폴백을 두지 않았다.** 키가 없을 때 인메모리 어댑터를 대신 올리면 "거래소에 포지션이
> 없다" 는 **거짓말이 화면에 뜬다.** 비어 있는 것과 알 수 없는 것은 다른 사실이고, 이 기능은
> 정확히 그 구분을 위해 있다.

> **실계좌 확인에서 드러난 것 — 키가 맞는데도 전부 거절됐다.**
>
> `-1021`. **이 기계의 시계가 바이낸스보다 33초 앞서 있었다.** 서명에 실린 타임스탬프가
> 거래소 기준 미래라 거절된다. 키·권한·IP 문제였다면 `-2015` 가 왔을 것이고, 그 구분은
> 오류 코드를 직접 봐야만 됐다 — 앱은 503 만 냈고 원인은 `ProblemDetail` 로 변환되며 사라졌다.
>
> **고친 자리는 코드다.** 타임스탬프의 목적은 "이 요청이 *거래소 시계 기준으로* 최신인가" 를
> 증명하는 것이므로 우리 시계를 쓰는 것은 틀린 시계에 묻는 것이다. 사람이 시계를 맞추는
> 쪽은 매번 다시 어긋나는 조건을 습관에 맡긴다. `BinanceServerClock` 이 공개 엔드포인트로
> 차이를 재고, **큰 차이는 경고로 남긴다** — 보정해도 그 차이는 캔들 구간과 체결 시각에
> 그대로 실리므로 조용히 고쳐 주면 안 된다.
>
> **그리고 이 기능이 첫 실행부터 실제 사례를 잡았다.** 계좌에 숏 0.114 가 열려 있는데
> 기록에 없었다(`EXCHANGE_ONLY`). 대조가 없었다면 현황 화면은 "진행 중인 거래가 없다" 라고만
> 말했을 것이다 — **덮어쓰기가 아니라 대조를 고른 이유가 첫 화면에서 증명됐다.**

**시크릿은 `.env` 로 받는다.** `spring.config.import` 로 읽고 `.gitignore` 가 막으며,
그 무시 규칙이 지워지는 것은 `SecretsAreNotCommittedTest` 가 막는다 — *"가린 것은 언젠가
실수로 커밋된다"* 는 Phase 8 의 문장이 여기서는 키에 걸린다.

**남은 것 둘.** - **AI 계획 초안이 422 를 낸다.** 키는 붙었고(503 이 아니다) 모델도 존재하는데, 문서에 적힌
  예제 문장조차 계획으로 읽히지 않는다. 추측해서 채우지 않는 것은 설계대로지만 이 문장은
  읽혔어야 한다. Phase 7 쪽 별건이다.
- **`liveAi` 가 전부 SKIPPED 다.** 그 테스트들은 `OPENAI_API_KEY` **환경변수**를 직접 보는데
  키는 이제 `.env` 에 있다. 앱에는 붙고 테스트에는 안 붙는다 — *"손으로 우회한 배선은
  검증되지 않는다"* 가 반대 방향으로 한 번 더 나온 것이다.
