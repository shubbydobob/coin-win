# ADR 015 — 지표 golden test 의 기준값은 합성 캔들과 손계산에서 얻는다

- 상태: 채택
- 날짜: 2026-08-21

## 맥락

Phase 4 완료 조건은 "트레이딩뷰 값과 일치" 다. 그런데 **트레이딩뷰 값은 코드로 가져올 수
없다.** 사람이 차트를 열어 읽는 수밖에 없다.

Phase 3 에서 같은 모양의 문제를 만났다. 청산가의 완료 조건이 "거래소 실제값과 일치" 였는데,
실제 청산가는 계좌 권한 없이 얻을 수 없었다(ADR 012). 그때의 해법은 *공개 공식과 공개
구간표로 손으로 푼 값*을 기준으로 삼고 오차 허용치 없이 센트 단위 일치를 요구하는 것이었다.

지표에서 위험한 것은 golden test 의 기댓값을 **구현을 돌려서 얻는** 것이다. 그렇게 하면
테스트는 "지금 코드가 지금 코드와 같다" 만 말하고, 공식이 틀려도 초록이다.

## 결정

기댓값은 **구현과 독립적으로 유도되는 두 종류의 입력**에서 얻는다.

**1. 닫힌 식이 나오는 합성 캔들.**

- 볼린저 — 공차 `d` 인 등차수열 `n` 개의 모집단 분산은 `d²(n²−1)/12` 다.
  `n=20, d=100` 이면 `332,500`, `σ = 576.6281297335…` 로 손에서 끝난다.
- 일목 — 단조 증가 캔들에서는 어느 구간이든 최고가가 마지막, 최저가가 첫 캔들에 있으므로
  `midpoint(i, p) = 60000 + 10i − 5(p−1)` 이라는 닫힌 식이 나온다.

**2. 극값이 구간 중간에 오는 비단조 캔들.**

단조 입력만으로는 "언제나 마지막 고가를 쓴다" 는 구현이 통과한다. 그래서 고가 200 을 구간
**첫머리**에 둔 13봉을 따로 만들고, 작은 설정(3/5/7, 변위 3)으로 다섯 선을 전부 손으로 푼다.

**트레이딩뷰 대조는 별도의 수동 절차로 남긴다.** 사람이 BTCUSDT 차트에서 값을 읽어 이 구현과
맞대 본 뒤, 결과를 [ADR 014](014-ichimoku-displacement-and-lagging-span.md) 에 기록한다.

## 근거

**공식이 틀렸는지 입력이 틀렸는지 구분된다.** 실제 캔들 스냅샷 하나로만 검사하면 값이
어긋났을 때 원인이 이동평균인지, 표준편차 종류인지, 창을 자르는 인덱스인지, 변위인지 알 수
없다. 닫힌 식 입력에서는 어느 항이 틀렸는지가 어긋난 값의 모양으로 드러난다.

**Phase 3 의 선례와 같은 논리다.** 외부 기준값을 자동으로 얻을 수 없을 때, *독립적으로 유도
가능한 값*을 기준으로 삼고 외부 대조는 사람이 한 번 한다. 이 편이 "대조할 값을 못 구해서
테스트를 못 쓴다" 보다 낫다.

**반올림 규칙도 같은 방식으로 고정한다.** 볼린저 상·하단은 스냅하지 않은 평균에서 계산한다.
평균이 `60000.005` 인 20봉을 만들어, 중심선을 스케일 2 로 먼저 스냅하면 하단이 `59999.97`,
스냅하지 않으면 `59999.96` 이 나오는 것을 회귀 테스트로 박아 두었다. **이 한 센트가 두 방식을
가른다.** 같은 원칙이 `projection` 의 자산 곡선에도 적용돼 있다(ADR 010).

## 한계

- **이 테스트들은 트레이딩뷰와의 일치를 증명하지 않는다.** 증명하는 것은 "구현이 명시된
  공식을 정확히 따른다" 까지다. 공식 해석 자체가 트레이딩뷰와 다르면 전부 통과하면서 값이
  어긋난다. 실제로 변위 26/25 가 그 지점이다(ADR 014).
- 합성 캔들은 실제 시장 데이터의 성질(갭, 동일가 연속, 극단적 변동성)을 담지 않는다.
  볼린저 하단이 음수가 되는 입력은 `Price` 가 음수를 금지하므로 예외가 된다 — BTC 가격대에서
  20봉 표준편차가 평균의 절반을 넘는 일은 없으므로 방어 코드를 두지 않았다.
- 볼린저 표준편차를 **모집단 기준**(n 으로 나눔)으로 정한 근거는 트레이딩뷰 `ta.stdev` 의
  `biased` 기본값이 true 라는 것이다. 이것은 Pine 레퍼런스에서 확인했으나, 표본 기준(n−1)으로
  바뀌면 20봉에서 약 2.6% 넓은 밴드가 나온다.
