# ADR 019 — AI 의 출력은 런타임에 검증한다

- 상태: 채택
- 날짜: 2026-08-22

## 맥락

ADR 005 는 AI 의 범위를 세 가지로 좁히면서 그 근거를 **검증 가능성**에 뒀다.

> 반면 구조화와 요약은 검증 가능하다. 파싱은 입력과 기대 출력을 고정할 수 있고,
> 요약은 원본 수치와 대조할 수 있다.

Phase 7 에서 그 문장을 코드로 옮기려니 질문이 하나 남았다 — **대조를 어디서 하는가.**
테스트에서만 하면 실제 응답은 검증되지 않은 채 나간다. 그러면 "검증할 수 있어서 허용했다"
는 근거가 허용의 이유로만 남고 실제로는 아무것도 검증하지 않는 것이 된다.

## 결정

**세 기능의 출력 규칙을 도메인 타입의 생성자에 둔다. 테스트가 아니라 운영 경로에서 돈다.**

| 기능 | 타입 | 규칙 | 어긴 출력의 운명 |
|---|---|---|---|
| 계획 파싱 | `DraftedFields` | 빈 칸이 있으면 계획이 되지 않는다 | 422, 무엇이 없는지 전부 |
| 결과 요약 | `Narrative` | 소수이거나 1000 이상인 수는 전부 원본에 있어야 한다 | 503 |
| 기록 질의 | `JournalAnswer` | 인용된 거래는 검색 결과 안에 있어야 한다 | 503 |

셋 다 **불완전한 인스턴스가 존재할 수 없다.** 검사를 통과하지 못한 출력은 응답이 되기 전에
예외가 된다.

## 근거

**틀린 출력은 조용히 퍼진다.** 지어낸 손절가는 잘못된 포지션 사이즈가 되고, 지어낸 승률은
전략 판단이 되고, 없는 거래를 인용한 답은 사용자가 그것을 찾지 못하는 순간부터 **맞는 답까지
믿을 수 없게** 만든다. 셋 다 발견이 늦을수록 대가가 커진다.

**규칙이 느슨한 쪽으로 조정된 곳이 두 군데 있다.** 반올림(`12.4567` → `12.5`)과 1000 미만
정수("두 가지", "3 번째")를 막으면 읽을 수 있는 문장이 나오지 않는다. 그래서 대조는
*쓰인 자릿수로 원본을 반올림해 같은지* 보고, 가격으로 오인될 수 없는 작은 정수는 통과시킨다.
**남은 구멍은 "약 6만" 같은 한국어 단위 표기**이며 프롬프트가 수를 그대로 쓰게 하는 것으로
막고 있다 — 규칙이 아니라 지침이므로 여기에 적어 둔다.

**상태 코드가 갈리는 기준은 입력에 사용자의 자유 텍스트가 있는가다.** 계획 파싱은 사용자가 쓴
문장을 받으므로 422(다시 써서 요청하면 된다)이고, 요약과 답변은 우리가 만든 수치와 검색
결과만 넘겼으므로 503(사용자가 고칠 것이 없다, 다시 시도할 일이다)이다.

## 결과

- **AI 응답의 품질을 테스트가 아니라 타입이 지킨다.** 모델을 바꿔도 규칙은 그대로다.
- 스텁 테스트와 실제 모델 테스트가 답하는 질문이 갈린다. 기본 `test` 는 "모델이 이렇게
  답하면 우리는 이렇게 한다" 만 증명하고, "모델이 이 문장에 이렇게 답한다" 는
  `.\gradlew.bat liveAi` 가 본다. Phase 4 의 `crossCheck` 와 같은 형태다.
- 프롬프트는 `resources/prompts/` 의 파일이므로 규칙이 바뀐 이력이 남는다(ADR 005).
