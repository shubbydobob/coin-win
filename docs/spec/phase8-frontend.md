# Phase 8 — 프론트엔드 명세

> 이 문서는 구현 전에 쓴다. Phase 6 과 7 에서 명세를 먼저 쓴 것이 각각 두 건의 오류를
> 코드 이전에 잡았다. 이 Phase 도 같은 순서로 간다.
>
> 근거 문서: `.claude/docs/scope.md`(무엇을 만들지), `.claude/docs/architecture.md`(모듈
> 경계), `.claude/docs/testing.md`(하네스 우선), `.claude/docs/conventions.md`(정책은 한 곳에).

---

## 1. 한 문장

**이미 있는 계산을 화면에 놓는다. 새 계산은 하나도 만들지 않는다.**

백엔드는 Phase 1~7 에서 16개 엔드포인트를 냈다. 이 Phase 가 더하는 것은 그 값을 사람이
읽을 수 있는 배치로 놓는 일뿐이다. 프론트엔드가 도메인 지식을 갖기 시작하면 같은 규칙이
자바와 타입스크립트 양쪽에 존재하게 되고, 그때부터 두 답이 갈라지는 것은 시간 문제다.

## 2. 확정된 선택

| 항목 | 선택 | 근거 |
|---|---|---|
| 위치 | `frontend/` (같은 리포) | 백엔드 DTO 와 프론트 타입이 한 커밋에서 함께 바뀐다 |
| 게이트 | `.\gradlew.bat check` 하나 | 게이트가 둘이면 하나는 반드시 안 돌게 된다 |
| 빌드 | Vite + React + TypeScript | 로드맵 지정 |
| 차트 | Recharts | 로드맵 지정 |
| 타입 | OpenAPI 스키마에서 생성 | 손으로 쓴 사본은 조용히 어긋난다 |
| 서버 상태 | TanStack Query | 로딩·오류·무효화를 직접 짜면 화면마다 다르게 짜게 된다 |
| 클라이언트 상태 | 없음 (전역 스토어 없음) | 중앙에 둘 만한 클라이언트 상태가 없다. YAGNI |
| 라우팅 | React Router | 화면 다섯 개 |
| 스타일 | Tailwind CSS | 밀도 높은 수치 표를 빨리 짠다. 되돌리기 쉬운 선택이다 |
| 테스트 | Vitest + Testing Library + MSW | 백엔드 없이 화면 전체를 돌린다 |
| Node | LTS 고정, `libs.versions.toml` 에 명시 | 버전은 이 파일 한 곳에만 존재한다 |

**전역 스토어를 두지 않는 이유**를 적어 둔다. 이 앱의 상태는 전부 서버에 있다. 진행 중인
거래도, 집계도, 백테스트 결과도 서버가 진실의 원천이다. 스토어를 두면 서버의 사본이 하나
생기고, 그 사본이 언제 낡는지를 관리하는 코드가 화면 수만큼 생긴다. TanStack Query 가
하는 일이 정확히 그것이므로 둘 다 두지 않는다.

**패키지 버전은 이 문서에 적지 않는다.** `frontend/package.json` 과
`gradle/libs.versions.toml` 에만 둔다. 여기에 적으면 세 번째 사본이 된다 —
`libs.versions.toml` 첫 줄이 금지하는 것과 같은 종류의 중복이다.

## 3. 이 Phase 의 유일한 어려운 규칙 — 프론트는 숫자를 만들지 않는다

화면에 나오는 모든 수는 **응답 본문에 그대로 있던 수**여야 한다.

금지되는 것:

```ts
// 금지 — 손익비를 프론트가 계산한다
const rr = (takeProfit - entry) / (entry - stopLoss);

// 금지 — 청산가 미리보기를 프론트가 만든다
const liq = avg * (1 - 1 / leverage);

// 금지 — 서버가 준 값을 다시 반올림한다
<td>{(res.maxLoss).toFixed(1)}</td>
```

허용되는 것:

```ts
// 허용 — 서버가 낸 값을 그대로 표시한다
<td>{money(res.maxLoss)}</td>

// 허용 — 사용자가 방금 타이핑한 입력값의 산술 표시
<span>비중 합계 {allocations.reduce((a, b) => a + b, 0)}</span>
```

**경계는 "그 수가 도메인 규칙의 결과인가" 다.** 사용자가 입력한 비중 50 과 50 을 더해 100
이라고 보여 주는 것은 산술이지 도메인 판정이 아니다. 그러나 그 옆에 "유효한 계획입니다" 를
붙이는 순간 `EntryLadder` 의 규칙이 두 곳에 생긴다. **합계는 보여 주되 판정은 서버에
맡긴다.**

### 3.1 규칙을 사람이 아니라 린트가 지킨다

`.claude/docs/roadmap.md` Phase 0 의 태도를 그대로 가져온다 — 규칙은 기억이 아니라 빌드가
지킨다. ESLint 로 강제한다.

| 금지 | 예외 | 잡는 실패 |
|---|---|---|
| `toFixed` `Math.round` `Math.floor` `Math.ceil` | `src/format/**` | 서버가 정한 스케일을 화면이 다시 반올림하는 것 |
| `parseFloat` `Number()` on 응답 값 | 입력 파싱(`src/form/**`) | 응답을 부동소수로 되돌려 계산에 쓰는 것 |
| feature 디렉터리 간 직접 import | 없음 | 백엔드 모듈 경계가 프론트에서 무너지는 것 |

세 번째는 `architecture.md` 의 "그 외 모듈 간 직접 참조 금지" 를 프론트에 옮긴 것이다.
`features/backtest` 가 `features/journal` 의 컴포넌트를 직접 부르기 시작하면 백엔드가 애써
나눈 경계가 화면에서 다시 붙는다. 공유가 필요하면 `shared/` 로 올린다.

**규칙이 실제로 발동하는지는 위반 픽스처로 증명한다.** Phase 0 이 ArchUnit 에 대해 한 것과
같은 형태다 — `frontend/eslint-fixture/` 에 일부러 어기는 파일을 두고, 그 파일에 대해 ESLint
가 정확히 그 규칙으로 실패하는지를 Vitest 가 단언한다. 통과하는 것처럼 보이지만 아무것도
매칭하지 않는 린트 규칙을 잡기 위해서다.

## 4. 디렉터리와 모듈 경계

```
frontend/
├── openapi.json               # 백엔드가 낸 스키마. 생성물이지만 커밋한다
├── src/
│   ├── api/
│   │   ├── schema.d.ts        # openapi-typescript 생성물. 손으로 고치지 않는다
│   │   ├── client.ts          # fetch 래퍼. ProblemDetail 파싱은 여기 한 곳
│   │   └── problem.ts         # ProblemDetail 타입과 판별
│   ├── format/                # 표시 형식. 여기서만 toFixed 를 쓴다
│   ├── form/                  # 입력 파싱. 여기서만 응답 아닌 문자열을 수로 바꾼다
│   ├── shared/                # 두 번째 화면이 쓰기 시작한 것만 올라온다
│   ├── features/
│   │   ├── overview/          # /              현황
│   │   ├── plan/              # /plan          포지션 계획 계산기
│   │   ├── journal/           # /journal       매매 기록
│   │   ├── backtest/          # /backtest      백테스트
│   │   └── projection/        # /projection    복리·몬테카를로
│   ├── routes.tsx
│   └── main.tsx
├── test/
│   ├── msw/                   # 핸들러와 픽스처
│   └── setup.ts
└── eslint-fixture/            # 일부러 규칙을 어기는 코드
```

`features/*` 는 백엔드 모듈과 이름이 같다. **일부러 같게 둔다** — 화면 하나가 어느 모듈을
소비하는지가 디렉터리 이름으로 읽혀야, 화면이 모듈 둘을 섞기 시작할 때 눈에 띈다.

`form/` 은 § 3.1 의 린트 예외 목록에만 있고 이 그림에서 빠져 있었다. 6단계에서 실제로
필요해져 만들었다 — **입력은 제출 전까지 글자**이므로 폼 상태는 문자열이고, 그것을 요청 본문의
수로 옮기는 자리가 하나 있어야 한다. `format/` 의 반대 방향이며, 린트가 두 방향을 디렉터리로
가른다.

`shared/` 는 **두 번째 사용처가 생겼을 때만** 만든다. `conventions.md` 의 "같은 로직이 두
번째 나타나면 즉시 추출한다" 를 그대로 적용하되, 세 번째를 기다리지도 않고 첫 번째에 미리
만들지도 않는다.

## 5. 타입은 백엔드가 낸다

### 5.1 흐름

```
Java DTO (@Schema)
   → springdoc
      → /v3/api-docs
         → frontend/openapi.json      (커밋)
            → openapi-typescript
               → src/api/schema.d.ts  (커밋)
                  → tsc
```

생성물 둘 다 커밋한다. 커밋하지 않으면 프론트를 빌드할 때마다 백엔드를 띄워야 하고,
그러면 프론트 테스트가 DB 와 Docker 에 묶인다.

### 5.2 스키마가 낡으면 빌드가 선다

커밋된 `openapi.json` 이 현재 자바 코드와 다르면 **`check` 가 실패한다.** 이것이 없으면
생성물을 커밋한 대가로 "손으로 쓴 사본" 과 똑같은 문제를 얻는다 — 백엔드 DTO 를 고치고
재생성을 잊으면 타입은 여전히 컴파일되고 런타임에만 틀린다.

검사는 **`@SpringBootTest` 로 한다.** `@WebMvcTest` 곡예가 필요 없다 — 테스트용
`application.yml` 이 Flyway 를 끄고 Hibernate 방언을 직접 알려 주어 **접속 0회로 전체
컨텍스트가 뜨게** 해 놓았고(Phase 3·5 에서 그렇게 만들었다), `OpenApiSmokeTest` 가 이미 그
위에서 `/v3/api-docs` 를 부르고 있다. 같은 자리에 파일 비교를 얹는다. DB 도 Docker 도 필요
없으므로 기본 `test` 에서 돈다.

**덤프가 실행마다 같은 바이트인지가 이 게이트의 전제였고, 확인했다**(§ 13.1). 다르면
게이트가 무작위로 깨져 아무도 믿지 않게 된다.

```
.\gradlew.bat openApiSchema     # 재생성. 위 테스트와 같은 경로로 만든다
.\gradlew.bat check             # 커밋된 파일이 현재 코드와 같은지 검사
```

**재생성은 한 명령이다.** `openApiSchema` 가 `openapi.json` 과 `schema.d.ts` 를 함께 만든다.
둘로 나누면 두 번째를 잊고, 그러면 스키마만 새것이고 타입은 낡은 상태가 된다 — 이 절이
없애려던 바로 그 상태다. `schema.d.ts` 가 `openapi.json` 과 같은지는 프론트 테스트가 본다.

**덤프 테스트는 기본 `test` 에서 걷어낸다.** 함께 돌면 낡음 검사가 자기가 방금 쓴 파일을
읽고 언제나 통과한다. `crossCheck` · `liveAi` 와 같은 형태다.

### 5.3 픽스처가 타입을 쓴다

MSW 핸들러가 돌려주는 가짜 응답을 생성된 타입으로 못 박는다.

```ts
const analysis: components["schemas"]["PositionAnalysisResponse"] = { ... };
```

백엔드 DTO 에서 필드가 사라지면 **테스트 픽스처가 컴파일되지 않는다.** 화면 코드보다 먼저
깨지는 자리를 만들어 두는 것이 요점이다.

### 5.4 그냥 생성하면 타입이 거짓말을 한다

**springdoc 은 `required` 를 내지 않는다.** 그대로 생성하면 모든 필드가 optional 이 된다.

```ts
SummaryResponse: {
    totalTrades?: number;
    profitFactor?: number;   // 실제로 오는 값은 null 이다. undefined 가 아니다
    netPnl?: number;         // 항상 있는데 optional 이다
};
```

두 가지가 한꺼번에 무너진다 — 항상 있는 값에까지 가드를 달게 되고(잡음), **진짜 null 인
것과 항상 있는 것이 구별되지 않는다**(위험). 뒤쪽이 § 6.4 의 "손익비 0 과 손익비를 말할 수
없음은 다른 사실" 을 타입 수준에서 지워 버린다.

**고치는 방법 둘 다 필요하다. 하나만 하면 더 나빠진다.**

1. **`OpenApiCustomizer` 한 개** — 이름이 `Response` 로 끝나는 스키마의 프로퍼티를 전부
   `required` 로 세운다. `common/config` 에 두고, DTO 40여 개에 애너테이션을 흩뿌리지
   않는다. 요청 스키마는 건드리지 않는다 — 요청은 실제로 선택 필드가 있고(`costs`,
   `topK`, `TradeQueryParams` 전부) 검증은 어차피 서버가 한다.
2. **진짜 null 인 필드에 `@Schema(nullable = true)`** — 설명 문구 옆이 그 표기의 자리다.
   설정에 목록을 두면 필드 지식이 두 곳에 생긴다.

> **구현 중에 드러난 것 — 2 만으로는 `$ref` 필드가 고쳐지지 않는다 (2026-08-22).**
>
> 스칼라는 초안대로다. `profitFactor` 는 `type: [number, "null"]` 로 나오고 타입도
> `number | null` 이 된다. **`$ref` 필드는 아니었다.** swagger-core 는 `nullable = true` 를
> `$ref` 옆에 형제 키로 붙인다 —
>
> ```json
> "entry": { "type": "null", "$ref": "#/components/schemas/EntryResultResponse" }
> ```
>
> JSON Schema 2020-12 에서 `$ref` 는 형제와 **합성**되므로 이것은 "null 이면서 동시에
> `EntryResultResponse`" 라는 뜻이다. 성립하지 않는 스키마이고, openapi-typescript 는 그냥
> 무시하고 `EntryResultResponse` 를 낸다.
>
> **애너테이션은 붙어 있는데 타입은 여전히 거짓말을 한다.** 그것도 이 절이 가장 위험하다고
> 지목한 방향으로 — 타입이 `entry` 는 언제나 있다고 단언하는데 `PLANNED` 상태에서는 null
> 이므로, 컴파일러가 가드를 지우게 만든다. **"1 만 하고 2 를 빠뜨리면 더 나쁘다" 는 문장이
> 맞았고, 다만 2 를 했는데도 그 상태가 되는 길이 하나 더 있었다.**
>
> 그래서 커스터마이저가 한 가지를 더 한다 — `$ref` 옆의 형제 null 표기를 `anyOf` 로 옮긴다.
> **여기에도 필드 목록은 두지 않는다.** "어느 필드가 null 인가" 는 DTO 애너테이션에만 있고,
> 커스터마이저는 그것을 *어떻게 표기하는가*만 고친다.
>
> 계약 테스트(`ResponseSchemaContractTest`)는 이제 형제 표기를 "null 을 받아들인다" 로 **세지
> 않는다.** 세면 통과하는 것처럼 보이면서 타입이 거짓말을 하는 상태가 초록으로 남는다.

**1 만 하고 2 를 빠뜨리면 optional 이던 시절보다 나쁘다** — `entry` 가 항상 있다고 타입이
단언하는데 `PLANNED` 상태에서는 null 이다. 컴파일러가 가드를 지우게 만든다.

**API 전체에서 null 이 오는 응답 필드는 정확히 셋이다.** 전수로 셌다.

| 필드 | 언제 null 인가 |
|---|---|
| `SummaryResponse.profitFactor` | 진 거래가 없는 표본 |
| `TradeResponse.entry` | `PLANNED` 상태 |
| `TradeResponse.outcome` | `PLANNED` · `OPEN` 상태 |

`TradeIntervals` 는 `Duration.ZERO` 를 쓰지 null 을 내지 않는다. 나머지는 전부 값이 있다.

**이것은 프론트를 위한 편의가 아니라 계약의 수정이다.** 지금 Swagger 는 손익비가 언제나
숫자라고 말하고 있고, 그것은 어느 소비자에게나 거짓이다.

## 6. 화면

### 6.1 `/` — 현황

지금 무엇이 열려 있는가에만 답한다.

| 블록 | 출처 |
|---|---|
| 진행 중인 거래 | `GET /api/trades/active` |
| 최근 집계 | `GET /api/trades/summary` |
| 시장 지표 | `GET /api/markets/BTCUSDT/metrics` |

시장 지표는 실패해도 화면이 죽지 않는다. 거래소가 안 닿는 것은 503 이고 (`DomainExceptionHandler`),
그 블록만 "가져오지 못했다" 로 두고 나머지는 그대로 보인다.

**차트를 두지 않는다.** 이 화면은 "지금 열려 있는 것" 이라는 질문 하나에 답하고 끝난다.

### 6.2 `/plan` — 포지션 계획 계산기

`POST /api/position-plans/analysis` 하나만 쓴다. **이 프로젝트의 본체다** — `scope.md` 의
문제 정의 1(분할 진입 시 총 리스크를 진입 전에 파악할 수 없다)에 직접 대응한다.

입력: 방향 · 진입 회차(가격·비중, 행 추가·삭제) · 손절가 · 익절가 · 레버리지 · 잔고 · 리스크%

출력이 이 화면의 핵심이다. `fillStates` 는 1건 체결부터 전량까지의 배열이고, **각 행이
"여기까지만 체결되면 이렇게 된다" 는 별개의 시나리오다.** 표로 놓는다.

```
체결   평단          수량           청산가        최대손실
1/2   60000.00     0.00266667     54216.87      10.67
2/2   59000.00     0.00533333     53313.25      16.00
```

같이 표시: `requiredMargin` · `riskRewardRatio` · `weakRiskReward`(손익비 1.5 미만 경고) ·
`marginExceedsBalance`(잔고 초과 경고).

**수량 입력란이 없다.** 수량은 손절가와 리스크 예산이 결정하는 출력이다. 입력란을 두면
사용자가 리스크 사이징을 건너뛴다 — Phase 7 이 계획 초안에서 총수량 칸을 뺀 것과 같은
이유다(`docs/spec/phase7-spring-ai.md` § 11).

경고 둘은 **입력을 막지 않는다.** 백엔드가 막지 않기로 했으므로 화면도 막지 않는다.

> **구현하며 정한 것 (2026-08-22).**
>
> **경고 문구에 기준값 1.5 를 적지 않는다.** 그 수는 `PositionPlan.MINIMUM_RISK_REWARD` 에
> 있고, 화면이 복창하면 백엔드가 기준을 바꿨을 때 **화면만 옛 숫자를 말한다.** § 3 이 수를
> 만들지 말라고 한 것과 § 7 이 문장을 짓지 말라고 한 것의 같은 뿌리다 — 도메인의 상수도
> 도메인의 문장과 같다. 대신 서버가 낸 손익비를 옆에 그대로 둔다.
>
> **빈 칸을 0 으로 채우지 않는다.** `Number("")` 는 0 이므로 그대로 두면 "잔고 0" 이라는
> 있지도 않은 값이 서버에 간다. 빈 칸은 `NaN` → `null` 로 실어 보내고 서버가 "누락된 필드" 로
> 답한다. 화면이 자체 검증 문장을 지으면 그것이 § 7 이 막으려던 두 번째 사본이다.
>
> **라우터를 화면 하나일 때 넣었다.** 화면의 정체는 그 URL 이고, 나중에 얹으면 화면들이 이미
> URL 없이 자란 뒤다. `/` 는 현황 화면이 마지막(12단계)이므로 그때까지 `/plan` 으로 보낸다.

### 6.3 `/journal` — 매매 기록

`scope.md` 문제 정의 2 에 대응한다. 하나의 화면 안에 세 부분이 있다.

**목록과 집계** — `GET /api/trades` 와 `GET /api/trades/summary` 에 **같은 조회 조건**이
걸린다(`TradeQueryParams`: 기간 · 방향 · 청산 이유 · 계획 준수 여부). 조건 UI 는 하나이고
두 요청에 같은 파라미터가 간다. 집계가 목록과 다른 모집단을 보고 있으면 화면이 거짓말을
한다.

집계에서 강조할 것은 승률이 아니라 **`costOfDeviation`** 이다. 계획을 어겨서 얻은 것의 합이고
음수면 어기는 편이 손해였다는 뜻이다. 이 프로젝트가 기록을 남기는 이유가 이 수치다.

**상태 전이** — `TradeResponse.state` 가 `PLANNED` / `OPEN` / `CLOSED` 이고, 상태마다 다음
동작이 정확히 하나다.

| 상태 | 화면이 내는 동작 | 엔드포인트 |
|---|---|---|
| `PLANNED` | 체결 기록 | `POST /api/trades/{id}/fills` |
| `OPEN` | 청산 기록 | `POST /api/trades/{id}/closure` |
| `CLOSED` | 없음 | — |

**상태를 프론트가 판정하지 않는다.** `state` 문자열을 그대로 보고 분기한다. `entry` 가
null 인지로 유추하면 백엔드가 상태를 하나 더 늘릴 때 화면이 조용히 틀린다.

청산 폼은 **손익을 입력받지 않는다.** 청산가·시각·이유·수수료·펀딩비만 받는다. 손익은
도메인이 체결 내역에서 계산한다(Phase 5). 손익 입력란을 두면 체결 내역과 손익이 어긋나
있어도 알 방법이 없어진다.

**질의(RAG)** — 같은 화면 안의 패널이다. § 6.6 참조.

### 6.4 `/backtest` — 백테스트

`POST /api/backtests` 를 중심으로, 같은 요청 본문을 세 엔드포인트가 공유한다.

| 버튼 | 엔드포인트 | 낸다 |
|---|---|---|
| 실행 | `POST /api/backtests` | 요약 · 거래 목록 · 자산 곡선 |
| 지표 필터 비교 | `POST /api/backtests/indicator-filter-comparison` | 기준 대 변경 |
| 비용 비교 | `POST /api/backtests/cost-comparison` | 기준 대 변경 |
| 요약 (AI) | `POST /api/backtests/narrative` | 문장 + 근거 수치 |

**캔들 동기화가 이 화면에 있어야 한다.** 백테스트는 저장된 캔들을 읽는데, 캔들을 넣는 길이
화면에 없으면 브라우저만으로는 백테스트를 한 번도 돌릴 수 없다.
`POST /api/markets/{symbol}/candles/sync` 를 구간 입력 옆에 둔다.

**차트는 자산 곡선 하나다.** `equityCurve` 는 거래마다 한 점이고 첫 점이 초기 자본이다.
가격 캔들 차트는 두지 않는다 — Phase 6 의 결론은 "이 규칙에는 엣지가 없다" 였고, 지금
필요한 것은 예쁜 차트가 아니라 **거래 목록을 눈으로 훑는 것**이다. `trades` 의 `rationale`
("지지대 59000.00~59200.00 (터치 3회) 근단 반전 진입")이 왜 그 거래가 섰는지를 문장으로
갖고 있다.

비교 응답(`ComparisonResponse`)은 `baseline` 과 `variant` 를 **나란히** 놓는다. 겹쳐 그리지
않는다 — 겹치면 어느 쪽이 무엇인지 보려고 범례를 읽어야 하고, 두 결과의 차이는
`pnlDifference` · `tradeDifference` 라는 수 두 개로 이미 나와 있다.

`profitFactor` 는 **null 일 수 있다**(진 거래가 없는 표본). `0` 으로 채우지 않는다 —
"손익비가 0" 과 "손익비를 말할 수 없다" 는 다른 사실이다. `—` 로 표시한다.

### 6.5 `/projection` — 복리 · 몬테카를로

같은 `ProjectionSpecRequest` 를 두 엔드포인트가 공유한다.

- `POST /api/projections/equity-curve` — 시드 하나의 표본 경로. 선 그래프.
- `POST /api/projections/monte-carlo` — N 회 분포.

**분포를 어떻게 그리는가가 이 화면의 유일한 판단이다.** 응답은 백분위 다섯 개
(`worst` · `p5` · `median` · `p95` · `best`)이지 히스토그램이 아니다. 없는 분포 모양을
그리지 않는다 — **다섯 점을 가진 구간 막대**로 놓고, 그 옆에 `lossProbability`(초기 자본에
못 미친 시행의 비율)와 `medianMaxDrawdown` · `worstMaxDrawdown` 을 수치로 둔다.

Phase 2 의 결론(`docs/adr/010`)이 "같은 기댓값에서도 경로에 따라 결과가 갈린다" 이므로,
이 화면이 답해야 하는 질문은 "얼마 버나" 가 아니라 **"운이 나쁘면 어디까지 가나"** 다.
`p5` 와 `worstMaxDrawdown` 을 중앙값보다 크게 놓는다.

### 6.6 AI 는 화면이 아니다

`/ai` 라우트를 만들지 않는다. `scope.md` 가 AI 를 **보조**로 한정했으므로 화면에서도
보조 자리에 둔다. 독립 화면을 만들면 "AI 에게 물어보는 곳" 이 생기고, 그것은 이 프로젝트가
하지 않기로 한 것(판단·추천)을 사용자가 기대하게 만드는 배치다.

| 기능 | 붙는 자리 |
|---|---|
| `POST /api/ai/plan-draft` | `/plan` 과 `/journal` 계획 작성 폼 위의 "문장으로 입력" |
| `POST /api/ai/journal-query` | `/journal` 안의 질의 패널 |
| `POST /api/backtests/narrative` | `/backtest` 결과 아래 |
| `POST /api/ai/reindex` | `/journal` 설정 구석 |

**계획 초안은 폼을 채울 뿐 제출하지 않는다.** `PlanDraftResponse` 를 받으면 입력란에 값을
넣고 거기서 멈춘다. 사용자가 본 다음에 제출한다. 422 로 "무엇이 빠졌는지" 가 오면 그
문장을 그대로 보여 준다(§ 7).

**질의 답변에는 근거 거래가 함께 온다.** `citedTradeIds` 는 목록의 해당 거래로 가는 링크로
만든다. 대조할 수 없는 답은 이 프로젝트에서 근거가 아니다 — `docs/adr/019` 가 런타임
검증을 도메인 생성자에 둔 것과 같은 태도다.

**AI 가 꺼져 있는 것은 고장이 아니다.** `OPENAI_API_KEY` 없이 앱이 그대로 뜨는 것이 Phase 7
의 완료 조건이었다. 503 을 받으면 해당 자리만 "AI 기능이 설정되지 않았다" 로 두고 나머지
화면은 전부 정상 동작한다. **AI 실패로 계획을 못 세우거나 기록을 못 남기는 일이 있으면
안 된다.**

## 7. 오류 — 프론트는 오류 문장을 짓지 않는다

백엔드는 RFC 7807 `ProblemDetail` 을 낸다. `detail` 에 도메인이 쓴 한국어 문장이 있다.

```json
{ "title": "도메인 규칙 위반", "status": 422,
  "detail": "롱 포지션의 손절가는 최저 진입가보다 낮아야 한다" }
```

**이 문장을 그대로 보여 준다.** 화면이 자기 문장으로 바꾸면 도메인 규칙의 표현이 두 곳에
생기고, 규칙이 바뀔 때 화면만 옛 문장을 말한다. 규칙 3 의 "숫자를 만들지 않는다" 와 같은
이유다 — **문장도 만들지 않는다.**

상태 코드별 화면 처리:

| 코드 | 뜻 | 화면 |
|---|---|---|
| 400 | 값이 유효하지 않다 | 폼 옆에 `detail` |
| 404 | 대상이 없다 | 목록으로 되돌리고 `detail` |
| 422 | 규칙 위반 | 폼 옆에 `detail`. 입력은 지우지 않는다 |
| 503 | 외부 데이터 · AI 미설정 | 해당 블록만 비활성. 다시 시도 버튼 |

400 과 422 를 화면이 구분하지 않는 것은 의도다. 사용자에게는 둘 다 "고쳐서 다시" 이고,
구분이 필요한 것은 부르는 코드지 사람이 아니다.

`client.ts` 한 곳에서만 응답을 판별한다. 화면 코드가 `res.status` 를 보는 일이 없어야 한다.
상태 코드를 화면에 넘기지 않으므로 갈래(`kind`)만 넘긴다 — `invalid` · `notFound` ·
`unavailable` · `unknown` 넷이다.

> **구현 중에 드러난 것 — 응답은 맞았고 스키마가 틀렸다 (2026-08-22).**
>
> 이 절은 "백엔드는 RFC 7807 `ProblemDetail` 을 낸다" 를 자명하게 두고 화면 처리만 정했다.
> **실제 응답은 맞았다.** 틀린 것은 그것을 소비자에게 알려 주는 자리였고, 셋이 한꺼번에
> 나왔다. 셋 다 검사하는 것이 아무것도 없었다.
>
> **하나 — 스키마가 오류 응답에 성공 DTO 를 씌우고 있었다.** springdoc 은 `@ApiResponse` 에
> 본문 타입이 없으면 **핸들러의 반환 타입**을 그대로 붙인다. 그래서 "계획 저장이 422 일 때
> `TradeResponse` 가 온다" 고 적혀 있었고, `ProblemDetail` 은 컴포넌트에 **아예 없었다.**
> § 5.4 와 같은 종류이고 더 나쁘다 — 소비자가 오류 본문을 성공 DTO 로 읽으려 하게 만든다.
> 커스터마이저 한 개로 고쳤고 **여기에도 엔드포인트 목록을 두지 않는다**: 오류 본문을 만드는
> 자리가 어드바이스 하나뿐이므로 규칙도 하나다 — *2xx 가 아닌 모든 응답의 본문은
> `ProblemDetail`*.
>
> **둘 — 19개 오퍼레이션 중 14개가 성공 응답을 선언하지 않고 있었다.** `@ApiResponses` 에
> 오류 코드만 적으면 springdoc 이 기본 200 을 **지운다.** 무엇을 돌려주는지가 스키마에서
> 통째로 사라지고, 생성된 타입에서 응답이 `never` 가 되어 **그 엔드포인트를 부르는 코드를
> 아예 쓸 수 없다.** 계획 계산기(§ 6.2)도 백테스트(§ 6.4)도 그 상태였다. 이것은 커스터마이저로
> 덮지 않고 각 `@ApiResponses` 에 한 줄씩 적었다 — 무엇을 돌려주는가는 엔드포인트마다 다른
> 사실이라 규칙으로 낼 수 없고, 그 한 줄이 다시 빠지는 것은
> `ResponseSchemaContractTest.모든_오퍼레이션은_성공_응답을_선언한다` 가 막는다.
>
> **셋 — RFC 의 다섯 칸을 그대로 적었더니 `type` 이 응답에 없었다.** 스프링은 기본값
> `about:blank` 를 직렬화에서 뺀다. 반대로 `instance` 는 언제나 온다. **RFC 를 읽어서는 알 수
> 없고 응답을 봐야 아는 것**이라, `ProblemDetailContractTest` 가 진짜 오류 응답의 키와 스키마를
> **양방향으로** 맞대 본다. 손으로 적은 목록이 실제와 갈라지는 것을 막는 유일한 방법이다.
>
> **그리고 이 절의 규칙에 예외가 둘 있다.** "프론트는 오류 문장을 짓지 않는다" 는 *오류에는
> 언제나 서버 문장이 있다* 를 전제하는데, 성립하지 않는 자리가 둘이다 — 요청이 서버에 닿지도
> 못한 경우와, 응답이 우리 어드바이스를 거치지 않아 `ProblemDetail` 이 아닌 경우(프록시가 낸
> HTML 따위). 도메인 규칙의 표현이 아니라 **전송 계층의 사실**이므로 두 곳으로 갈라질 것이
> 없고, `problem.ts` 안에 상수 둘로만 존재한다.

## 8. 표시 형식

값 객체의 스케일은 `conventions.md` 에 있다 — `Price` 2, `Quantity` 8, `Money` 2,
`Percentage` 4.

**JSON 숫자는 자바스크립트에서 `60000.00` 이 아니라 `60000` 이 된다.** 스케일 정보가 파싱에서
사라지므로 표시할 때 되살려야 한다. `src/format/` 이 그 한 곳이다.

```ts
price(v)     // 2자리, 천단위 구분
quantity(v)  // 8자리
money(v)     // 2자리
percent(v)   // 4자리 + %
ratio(v)     // 2자리 — 손익비처럼 단위 없는 배수
```

`ratio` 는 초안에 없었다. 값 객체가 아니라 도메인이 직접 정한 자릿수(`PositionPlan.RATIO_SCALE`)
이고, 손익비를 `price` 로 찍으면 자릿수는 맞지만 뜻이 틀린다. **서버가 그것을 버림으로 내는
이유가 있으므로**(1.495 를 반올림하면 경고는 켜졌는데 화면은 기준을 넘은 것처럼 보인다) 화면도
그 자릿수를 줄이지 않는다.

**이것은 정책의 두 번째 사본이 맞다.** 그럼에도 두는 이유와, 그럼에도 안전한 이유:

- 두는 이유 — 스케일을 지우지 않고 넘기려면 응답 숫자를 문자열로 바꿔야 하고, 그것은
  기존 API 계약과 OpenAPI 스키마 타입(`number` → `string`)을 전부 바꾸는 일이다.
  화면 하나 때문에 백엔드 계약을 바꾸지 않는다.
- 안전한 이유 — 이 사본은 **표시 자릿수**만 갖고 **반올림 정책**은 갖지 않는다. 계산이
  없으므로 갈라질 값이 없다. `conventions.md` 가 막으려는 것("계산 결과가 갈라진다")은
  계산에서 오지 표시에서 오지 않는다.
- 그럼에도 지키는 규칙 — **스케일을 줄여서 표시하지 않는다.** 서버가 정한 자릿수 그대로
  낸다. 줄이면 그 순간 브라우저가 반올림을 하게 되고, 위 두 번째 이유가 무너진다.

`format` 밖에서 `toFixed` 를 부르는 것은 린트가 막는다(§ 3.1).

> **구현하며 정한 것 셋 (2026-08-22).**
>
> - **천단위 구분은 `price` 와 `money` 둘 다에 붙인다.** 초안은 `price` 에만 적었는데, 그 둘은
>   같은 표 안에 나란히 놓이고(청산가 54,216.87 옆의 최대손실) 자릿수가 같은 크기다. 한쪽만
>   구분이 있으면 다른 종류의 수로 읽힌다. `quantity` 는 이 증거금 규모에서 언제나 1 미만이고
>   `percent` 는 0~100 이라 붙일 자리가 없다.
> - **로케일을 환경에 맡기지 않는다.** 맡기면 같은 값이 사람마다 다르게 보이고, 테스트가
>   통과하는 컴퓨터와 아닌 컴퓨터가 갈린다. 숫자 표기는 언어 설정이 아니라 `format/` 이 정한다.
> - **`percent` 는 100 을 곱하지 않는다.** `Percentage` 가 이미 100 기준이다
>   (`DecimalValues.ratio` 가 ×100 을 한다). 승률 1/3 은 `33.3333` 으로 온다. 프론트가 곱하면
>   그것이 § 3 이 금지한 계산이 되고, 곱하지 않는 것이 마침 옳기도 하다.
>
> `Duration` 은 아직 두지 않았다. § 13.2 가 "첫 사용처에서 정한다" 이고 그 자리는 `/journal`
> (8단계)이다. 쓰는 곳 없이 형식을 먼저 정하면 `PT26H30M` 을 어떻게 읽어야 하는지를 화면
> 없이 상상하게 된다.

시각은 `Instant`(UTC)로 온다. **UTC 로 표시하고 `UTC` 를 붙인다.** 로컬 타임존으로 바꾸면
캔들 시각·체결 시각과 어긋나 보인다. 기간은 ISO-8601 `Duration`(`PT8H`)으로 오므로
`8시간` 으로 옮긴다 — 이것은 표시 변환이지 계산이 아니다.

## 9. 빌드 배선

### 9.1 Gradle 연동

```
.\gradlew.bat check
  ├── (기존 자바 게이트 전부)
  ├── openApiSchemaCheck    커밋된 openapi.json 이 현재 코드와 같은가 (§ 5.2)
  └── frontendCheck         tsc --noEmit · eslint · vitest run
```

`com.github.node-gradle.node` 플러그인을 쓴다. **로컬에 설치된 npm 을 부르지 않는다** —
Node 버전이 사람마다 다르면 "내 컴퓨터에서는 되는데" 가 그대로 재발한다. 플러그인이 지정
버전을 내려받고 Windows 의 `npm.cmd` 도 알아서 다룬다. 버전은 `libs.versions.toml` 에 둔다.

`frontendCheck` 는 `openApiSchemaCheck` 다음에 돈다. 스키마가 낡았다면 타입 오류의 원인이
그것이므로 먼저 실패하는 편이 읽기 쉽다.

### 9.2 개발 중

```powershell
docker compose up -d db
.\gradlew.bat bootRun              # 8080
cd frontend; npm run dev           # 5173, /api 와 /v3 를 8080 으로 프록시
```

**백엔드에 CORS 설정을 넣지 않는다.** Vite dev 서버의 프록시로 같은 오리진이 되므로 필요가
없고, 넣으면 운영에도 없는 설정이 개발에만 존재하게 된다.

### 9.3 패키징

`npm run build` → `frontend/dist` → Gradle 이 `build/resources/main/static/` 으로 복사.
`src/main/resources/static` 에 넣지 않는다. 생성물이 소스 트리에 들어오면 `.gitignore` 로
가려야 하고, 가린 것은 언젠가 실수로 커밋된다.

`bootJar` 하나에 백엔드와 프론트가 함께 들어간다. 1인 사용 전제에서 배포 대상이 둘일 이유가
없다.

### 9.4 SPA 라우트 되돌리기

`/journal` 을 새로고침하면 서버가 그 경로를 받는다. `index.html` 로 포워드해야 한다.
`common/config` 에 `WebMvcConfigurer` 를 하나 둔다.

**`/api` · `/v3/api-docs` · `/swagger-ui` · `/assets` 는 삼키지 않는다.** 특히 Swagger UI 는
Phase 0 부터 있던 것이고, 프론트가 그것을 가리면 API 문서가 조용히 사라진다.

이 클래스는 `domain` 이 아니므로 ArchUnit 규칙 1 에 걸리지 않고, `common/config` 는 이미
있는 자리다. **Phase 8 이 손대는 유일한 자바 코드가 이것이다** — 그리고 § 5.2 의 스키마
검사 테스트.

## 10. 검증 하네스

`testing.md`: **어떤 프로덕션 코드도 검증 하네스 없이 작성하지 않는다.** 화면도 프로덕션
코드다.

### 10.1 화면마다 세 상태

**모든 화면은 성공 · 오류 · 로딩 세 상태의 테스트를 갖는다.** 커버리지 퍼센트를 게이트로
두지 않는 대신 이 세 개를 규칙으로 둔다. 백엔드가 `domain` 90% 를 요구하는 자리에 대응한다.
퍼센트가 아닌 이유는 프론트의 대부분이 배치이고, 배치의 커버리지 수치는 무엇도 증명하지
않기 때문이다.

### 10.2 이름은 문장으로

```ts
it("체결 상태 표는 응답에 온 행 수만큼 나온다")
it("손익비가 1.5 미만이면 경고가 보이지만 제출은 막히지 않는다")
it("422 응답의 detail 문장이 그대로 화면에 나온다")
it("AI 가 503 이면 그 패널만 비활성이고 계획 저장은 그대로 된다")
it("PLANNED 거래에는 청산 버튼이 없다")
it("진 거래가 없는 백테스트의 손익비는 0 이 아니라 — 로 나온다")
```

`testing.md` 의 한글 테스트 이름 규칙을 그대로 가져온다.

### 10.3 반드시 있어야 하는 테스트

| 무엇을 지키는가 | 테스트 |
|---|---|
| § 3 숫자를 만들지 않는다 | 픽스처의 수치가 화면에 **문자열로 그대로** 나온다 |
| § 3.1 린트가 실제로 잡는다 | `eslint-fixture/` 가 지정된 규칙으로 실패한다 |
| § 6.3 상태 전이 | 세 상태 각각에 나오는 동작 버튼이 정확히 맞다 |
| § 6.4 null 손익비 | `profitFactor: null` 이 `—` 로 나온다 |
| § 6.6 AI 격리 | AI 엔드포인트만 503 인 상태에서 나머지 화면이 전부 동작한다 |
| § 7 오류 문장 | `detail` 이 가공 없이 나온다 |
| § 8 스케일 | 값 객체 스케일 네 개가 각각 유지된다 |

### 10.4 E2E 는 두지 않는다

Playwright 를 넣지 않는다. MSW 가 네트워크 층에서 가로채므로 화면은 실제 요청 경로를 그대로
타고, 검증되지 않고 남는 것은 **"백엔드가 정말 그 모양으로 응답하는가"** 하나다. 그것은
§ 5.2 의 스키마 검사가 타입 수준에서 잡는다.

남는 구멍을 적어 둔다 — **스키마가 같아도 값이 다를 수 있다.** 통합 동작은 사람이 한 번
훑는다. `crossCheck` · `liveAi` 와 같은 종류의 자리이고, 자동화하지 않기로 한 것이지
잊은 것이 아니다.

## 11. 완료 조건

로드맵의 Phase 8 은 조건이 적혀 있지 않다. 여기서 정한다.

1. `.\gradlew.bat check` 가 자바 게이트와 프론트 게이트를 **한 번에** 통과한다.
2. `OPENAI_API_KEY` 없이 다섯 화면이 전부 동작한다. AI 자리만 비활성이다.
3. 브라우저만으로 **실제 매매 1건**이 처음부터 끝까지 기록된다 — 계획 저장 → 체결 → 청산 →
   집계 반영. Phase 5 의 완료 조건을 화면으로 다시 통과하는 것이다.
4. 브라우저만으로 백테스트를 한 번 돌린다 — 캔들 동기화부터 자산 곡선까지.
5. 백엔드 DTO 필드 하나를 지우면 `check` 가 실패한다. (§ 5.2 가 실제로 발동하는지의 증거.
   확인은 임시 파괴가 아니라 **위반 픽스처**로 한다 — `.claude/docs/roadmap.md` Phase 0 과
   같은 이유다.)
6. 생성된 타입에서 `profitFactor` · `entry` · `outcome` 이 **null 을 포함하고**, 나머지
   응답 필드는 optional 이 아니다. (§ 5.4 가 실제로 걸렸다는 증거)
7. `bootJar` 하나를 실행해 프론트와 API 와 Swagger UI 가 모두 뜬다.

## 12. 구현 순서

각 단계는 `check` 가 통과하는 상태로 끝난다.

1. **배선만** — Vite 프로젝트 생성, Gradle 연동, 빈 화면 하나, `check` 통과.
2. **스키마를 정직하게 만든다** — § 5.4 의 커스터마이저 하나와 `nullable` 셋. **프론트보다
   먼저 한다.** 순서를 바꾸면 거짓 타입 위에 화면을 짓고 나중에 전부 다시 본다.
3. **타입 생성 경로** — `openApiSchema` 태스크와 낡음 검사. 위반 픽스처로 발동 확인.
4. **`client.ts` 와 `ProblemDetail`** — 오류 처리가 첫 화면보다 먼저 있어야 화면마다 다르게
   짜지 않는다.
5. **`format/` 과 그 테스트** — 스케일 네 개.
6. **`/plan`** — 가장 단순하고(POST 하나) 프로젝트의 본체다. 여기서 화면 하나의 모양을
   확정한다.
7. **ESLint 규칙과 픽스처** — 화면이 하나 있어야 규칙이 현실적인지 안다.
8. **`/journal`** — 가장 복잡하다. 목록·집계·상태 전이.
9. **`/backtest`** — 첫 차트. 캔들 동기화 포함.
10. **`/projection`** — 두 번째 차트. 여기서 차트 공통 부분이 `shared/` 로 올라간다
   (두 번째 사용처가 생긴 시점이다).
11. **AI 보조 세 자리** — 마지막. AI 없이 전부 도는 것을 먼저 증명한 뒤에 얹는다.
12. **`/` 현황** — 앞의 것들을 재사용해 얇게.
13. **SPA 포워딩과 패키징** — `bootJar` 하나로 뜨는 것 확인.

**AI 를 마지막에 두는 것이 순서의 요점이다.** 먼저 얹으면 "AI 없이도 전부 된다" 를 증명할
기회가 사라진다.

## 13. 미확정 — 구현 시작 전에 확인한다

### 13.1 스키마 덤프 — 닫혔다 (2026-08-22)

구현 전에 스파이크로 확인했다. 세 가지를 물었고 셋 다 답이 나왔다.

- **DB·Docker 없이 덤프되는가 — 된다.** `@WebMvcTest` 는 필요 없었다. 기존
  `OpenApiSmokeTest` 가 이미 `@SpringBootTest` 로 접속 0회 컨텍스트 위에서 `/v3/api-docs`
  를 부르고 있다. 명세 초안이 어려운 길을 가정하고 있었다.
- **실행마다 같은 바이트인가 — 그렇다.** 독립 JVM 3회의 출력이 47,453 바이트로 완전히
  동일했다. 커스터마이저(§ 5.4)를 얹은 뒤에도 다시 확인했다.
- **openapi-typescript 가 이 스키마를 먹는가 — 먹는다.** 7.13.0 / 스키마 42개 · 경로 19개.
  다만 **그냥 먹이면 타입이 거짓말을 한다** — 그것이 § 5.4 이고, 이 스파이크의 진짜 수확이다.

`Duration` 은 `{"type": "string"}` 으로 나온다(포맷 없음). § 13.2 는 그대로 열려 있다.

### 13.2 `Duration` 표시

`PT8H` 는 옮기기 쉽지만 `PT26H30M` 은 "26시간 30분" 인가 "1일 2시간 30분" 인가.
`holdingPeriod` 와 `intervals` 두 곳에 나온다. **첫 사용처에서 정하고 `format/` 에 한 번만
둔다.**

### 13.3 백테스트 거래 목록의 크기

Phase 6 의 실측에서 한 실행이 119건까지 나왔다. 가상 스크롤이 필요한 규모는 아니지만
`ComparisonResponse` 는 그 목록을 **두 벌** 담는다. 먼저 그냥 그리고, 느리면 그때 자른다 —
자를 때는 **잘랐다는 사실을 화면에 적는다.** 조용한 잘라내기는 "전부 봤다" 로 읽힌다.

### 13.4 ADR 020

이 Phase 의 판단 중 ADR 로 남길 것은 **§ 3(프론트는 숫자를 만들지 않는다)** 이다.
구현이 끝난 뒤, 실제로 어디서 이 규칙이 유혹을 받았는지를 함께 적어 쓴다. 유혹받은 자리가
없었다면 그 규칙은 자명했던 것이므로 ADR 이 필요 없다.

## 14. 이 명세가 틀릴 수 있는 곳

Phase 6 과 7 에서 명세가 각각 두 군데 틀렸고, 둘 다 **"이 문장이 코드에서 무엇이 되는가"**
를 물었을 때 드러났다. 이 문서에서 가장 의심스러운 문장 셋을 미리 적어 둔다.

- ~~**§ 5.2 "DB 도 Docker 도 필요 없다"**~~ — 확인됐다(§ 13.1). 그런데 **이 문장이 맞다는
  것을 확인하는 과정에서 § 5.4 가 나왔다.** 초안은 "스키마를 생성하면 타입이 생긴다" 를
  자명하게 여겼는데, 생성된 타입은 `profitFactor` 가 null 일 수 있다는 것을 말하지 못했다.
  Phase 6·7 과 같은 종류다 — **틀린 것은 검증하려던 문장이 아니라 그 문장이 전제하던
  다른 문장이었다.**
- ~~**§ 5.4 "`nullable = true` 를 붙이면 타입이 `T | null` 이 된다"**~~ — 스칼라만 그랬다.
  `$ref` 필드는 애너테이션을 붙여도 타입이 여전히 거짓말을 했다. 위 § 5.4 의 인용 블록에
  적었다. **이번에도 틀린 것은 검증하려던 문장이 아니라 그 문장이 전제하던 다른 문장이었다** —
  "3.1 의 nullable 표기는 한 가지다" 를 자명하게 여겼는데 두 가지였고 하나는 무효였다.
- ~~**§ 7 "백엔드는 RFC 7807 `ProblemDetail` 을 낸다"**~~ — 응답은 그랬고 **스키마는 아니었다.**
  오류 응답에 성공 DTO 가 씌워져 있었고, 그 김에 14개 오퍼레이션이 성공 응답을 아예 선언하지
  않고 있는 것도 드러났다. 위 § 7 의 인용 블록에 적었다. **세 번째로 같은 모양이다** — 틀린
  것은 검증하려던 문장이 아니라 그 문장이 전제하던 다른 문장이었고, 이번에 전제는
  "응답이 그러면 스키마도 그렇다" 였다. 생성물을 소비하는 쪽에서 **응답과 스키마는 다른
  사실이다.**
- **§ 3 "허용되는 것: 입력값의 산술 표시"** — 경계가 말처럼 선명하지 않을 수 있다. 비중
  합계는 산술이지만, 진입가 배열의 최소·최대를 구해 손절가와 비교해 보이는 것은? 그것은
  이미 도메인 규칙이다. 구현 중에 이 경계에서 걸리는 사례가 나오면 § 3 에 예로 추가한다.
- **§ 6.5 "다섯 점을 가진 구간 막대"** — 백분위 다섯 개를 어떻게 놓아야 "운이 나쁘면 어디까지
  가나" 가 읽히는지는 그려 봐야 안다. 안 읽히면 배치를 바꾸되 **없는 분포를 그리지는
  않는다** 는 제약만 지킨다.
