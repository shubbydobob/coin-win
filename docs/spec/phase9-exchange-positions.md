# 거래소 포지션 대조 — 명세

> 로드맵의 Phase 가 아니라 **개별 변경**이다. 그럼에도 명세를 먼저 쓰는 이유는 Phase 6·7·8
> 이 세 번 같은 것을 확인했기 때문이다 — "이 문장이 코드에서 무엇이 되는가" 를 물었을 때만
> 틀린 전제가 드러난다.

## 1. 한 문장

**기록의 `OPEN` 거래와 거래소의 실제 포지션을 나란히 놓고, 어긋나면 그 사실을 드러낸다.**

## 2. 왜 "대체" 가 아니라 "대조" 인가

현황 화면의 "진행 중인 거래" 는 지금 **우리 DB 의 `OPEN` 상태 매매**를 뜻한다. 거래소가 말하는
포지션은 **다른 사실**이다. 둘은 이렇게 갈린다.

| 상황 | 기록 | 거래소 |
|---|---|---|
| 계획대로 열고 적었다 | `OPEN` | 포지션 있음 |
| 앱 밖에서 열었다 (모바일 앱 등) | 없음 | 포지션 있음 |
| 닫았는데 청산을 안 적었다 | `OPEN` | 없음 |
| 손절이 체결됐는데 모르고 있다 | `OPEN` | 없음 |
| 물타기를 추가로 했다 | `OPEN` (수량 A) | 포지션 (수량 B) |

**거래소 값으로 덮어쓰면 아래 네 줄이 전부 사라진다.** 화면은 언제나 "맞는" 것처럼 보이고,
계획 준수율 집계는 기록에만 기대므로 조용히 틀린 값을 낸다. 이 프로젝트가 푸는 문제 둘 중
하나가 "매매 이력이 구조화되지 않아 사후 분석이 불가능하다" 인데, **적기를 빠뜨린 것을 잡아
주는 것**이 그 문제에 직접 기여한다.

> **기록이 진실의 원천이라는 원칙은 그대로다.** 거래소는 *지금 이 순간의 사실*을 알지만
> *내가 무엇을 하려 했는지*는 모른다. 계획 준수·반사실·거래 간격은 전부 기록에서만 나온다.
> 거래소 값은 **대조 대상**이지 원천이 아니다. `ai` 의 인덱스가 파생인 것과 같은 자리다.

## 3. 새 모듈 `account`

`market` 에 두지 않는다. `market` 은 **모두에게 같은 사실**(캔들·펀딩비·OI)이고 서명이 필요
없다. 포지션은 **내 계좌의 사실**이고 서명이 필요하다. 한 모듈에 섞으면 "이 어댑터는 키가
있어야 도는가" 가 클래스마다 달라진다.

```
com.coinwin.account/                 # ◆ 포트/어댑터
├── domain/                          # ExchangePosition, PositionMatch, PositionReconciliation
├── application/
│   ├── port/in/                     # ReconcilePositionsUseCase
│   ├── port/out/                    # LoadExchangePositionsPort
│   └── service/                     # PositionReconciliationService
└── adapter/
    ├── in/web/                      # AccountController
    └── out/
        ├── binance/                 # BinancePositionAdapter (서명), BinanceSigner
        └── memory/                  # InMemoryExchangePositionAdapter
```

**포트를 두는 근거는 ADR 002 의 기준 그대로다** — 구현체가 실제로 둘이다(binance / 인메모리).
`journal` 과 같은 이유이고, "DB 없이 도메인 테스트를 돌린다" 가 여기서는 "키 없이 서비스
테스트를 돌린다" 가 된다.

### 의존 방향

```
account → journal.application.port.in, journal.domain, position.domain, common
journal → account 는 금지
```

`ai → journal` 과 같은 모양이다. 대조하는 쪽이 기록을 읽고, 기록은 대조를 모른다.
**방향이 반대가 되면 `journal` 이 키와 네트워크에 묶인다.**

## 4. 도메인

```java
/** 거래소가 말하는 지금 이 순간의 포지션. */
public record ExchangePosition(
        Symbol symbol, Direction direction, Quantity quantity,
        Price entryPrice, Optional<Price> liquidationPrice, Money unrealizedPnl,
        Instant observedAt)
```

**수량 0 인 포지션은 포지션이 아니다.** 바이낸스는 닫힌 심볼도 `positionAmt: "0"` 으로 돌려
준다. 그것을 그대로 담으면 "포지션 있음" 이 되어 대조가 통째로 뒤집힌다. **어댑터에서
걸러 낸다.**

**방향은 부호에서 읽는다.** `positionAmt` 가 양수면 롱, 음수면 숏이다. 수량은 절대값이다.

> **청산가가 `Optional` 인 것도 구현이 잡았다.** 초안은 `Price` 였는데, 바이낸스는 청산 지점을
> 말할 수 없을 때 `"0"` 을 준다. 0 원짜리 청산가로 담으면 화면이 **"곧 청산된다"** 는 뜻으로
> 읽는다. 손익비를 `Optional` 로 둔 것과 같은 규칙이다 — **말할 수 없는 것을 0 으로 적지
> 않는다.**

```java
/** 기록 한 건과 거래소 포지션 한 건을 맞춰 본 결과. */
public sealed interface PositionMatch {
    record Agreed(OpenTrade recorded, ExchangePosition actual) implements PositionMatch {}
    record RecordedOnly(OpenTrade recorded) implements PositionMatch {}
    record ExchangeOnly(ExchangePosition actual) implements PositionMatch {}
    record QuantityDiffers(OpenTrade recorded, ExchangePosition actual) implements PositionMatch {}
}
```

**`sealed` 로 두는 이유는 Phase 5 의 `Trade` 와 같다.** 네 경우를 `boolean matched` 하나로
줄이면 "기록만 있다" 와 "수량이 다르다" 가 같은 값이 되고, 화면이 그 둘에 다른 말을 할 수
없다. 대응이 다른 사실은 타입이 달라야 한다.

- `RecordedOnly` → **청산을 적지 않았을 가능성.** 사람이 확인하고 청산을 기록해야 한다
- `ExchangeOnly` → **앱 밖에서 연 포지션.** 기록에 계획이 없다
- `QuantityDiffers` → 물타기·부분 청산이 기록되지 않았다

```java
/** 대조 한 번의 결과. */
public record PositionReconciliation(List<PositionMatch> matches, Instant observedAt) {
    public boolean isConsistent()      // 전부 Agreed 인가
    public List<PositionMatch> discrepancies()
}
```

### 맞추는 키 — 심볼이 아니라 방향이다

> **초안은 "심볼로 맞춘다" 였고 그것은 틀렸다.** `OpenTrade` 에 **심볼이 없다.** 이 프로젝트는
> BTC 무기한 하나만 다루므로(`scope.md`) 기록이 종목을 적지 않는다. 구현하면서 드러났다.

**방향으로 맞춘다.** 한 종목에 대해 롱 포지션과 숏 포지션은 각각 최대 하나씩만 존재할 수
있으므로 방향은 짝을 정하는 키로 충분하다.

이 선택이 더 나은 모양을 만들었다. **기록은 롱인데 거래소가 숏이면 `RecordedOnly` 와
`ExchangeOnly` 가 각각 하나씩 나온다** — 짝이 지어지지 않는 것이 곧 사실의 표현이다. 심볼로
맞췄다면 한 줄로 합쳐지고, "방향이 뒤집혔다" 는 가장 심각한 사실이 수량 불일치처럼 보였을
것이다.

**종목 거르기는 서비스가 한다.** 도메인은 이미 걸러진 목록을 받는다 — 거래소는 계좌의 모든
심볼을 돌려주므로 그 필터가 없으면 다른 종목의 포지션이 우리 기록과 짝지어진다.

### 수량 비교

`Quantity` 는 스케일 8 이다. **정확히 같아야 `Agreed`** 다. 허용 오차를 두면 그 값이 어디서
왔는지 설명할 수 없고, 부분 체결이 조용히 통과한다.

## 5. 서명

바이낸스 개인 엔드포인트는 HMAC-SHA256 이다.

```
GET /fapi/v3/positionRisk?timestamp={ms}&recvWindow=5000&signature={hex}
X-MBX-APIKEY: {apiKey}
```

- 서명 대상은 **정렬하지 않은 원본 질의 문자열 그대로**다. 순서를 바꾸면 서명이 깨진다
- `timestamp` 는 서버 시각과 `recvWindow` 안이어야 한다. 로컬 시계가 밀리면 `-1021` 이 온다

> **이 줄이 실제로 터졌다.** 개발 기계가 33초 앞서 있어 **모든 요청이 거절**됐다. 명세가
> 위험을 적어 두고도 대책을 적지 않았던 자리다.
>
> 고치는 방법이 둘로 보였다 — 사람이 시계를 맞추거나, 코드가 보정하거나. **후자가 옳다.**
> 타임스탬프의 목적은 "이 요청이 **거래소 시계 기준으로** 최신인가" 를 증명하는 것이므로,
> 우리 시계를 쓰는 것은 애초에 틀린 시계에 묻는 것이다. 전자는 매번 다시 어긋나는 조건을
> 사람의 습관에 맡긴다.
>
> `BinanceServerClock` 이 공개 엔드포인트 `/fapi/v1/time` 으로 차이를 재고 15분마다 다시
> 잰다. **큰 차이는 경고로 남긴다** — 보정해서 요청은 통과해도 기계 시계가 어긋난 사실 자체는
> 캔들 조회 구간과 체결 시각에 그대로 실린다. 조용히 고쳐 주면 그 사실이 사라진다.
>
> 보정의 **부호가 반대면 증상이 그대로 남고 오히려 두 배로 어긋난다.** 그래서 테스트가 앞뒤
> 양방향을 모두 못 박는다.
- **시크릿은 로그에 절대 나오지 않는다.** 서명 실패 메시지에도 질의 문자열을 넣지 않는다

`BinanceSigner` 하나가 이 일만 한다. 순수 함수라 테스트로 고정할 수 있다 — **바이낸스 공개
문서의 예제 벡터**로 검증한다(키·시크릿·질의·기대 서명이 문서에 있다).

## 6. 키가 없을 때

**Phase 7 의 AI 와 같은 형태다.** 키가 없으면 `BinancePositionAdapter` 빈이 올라오지 않고,
`/api/account/positions` 만 503 을 낸다. 앱과 나머지 화면은 그대로 뜬다.

`.\gradlew.bat check` 는 **키 없이 통과해야 한다.**

> **`liveAccount` 태스크는 만들지 않았다.** `crossCheck` · `liveAi` 와 같은 형태를 생각했지만,
> 그 둘은 *출력을 사람이 읽는* 도구인 반면 여기서 볼 것은 **화면**이다. 표를 콘솔에 찍어도
> 확인하려는 것(대조가 화면에서 어떻게 보이는가)이 확인되지 않는다. Phase 8 이 남긴 것도
> 같은 결론이다 — **사람이 한 번 띄워 보는 것 말고는 막을 방법이 없다.** 그래서 실계좌
> 확인은 § 9 의 7번, 브라우저 하나로 둔다.

> 이것이 이 명세에서 가장 쉽게 어겨질 규칙이다. 키가 있는 개발 기계에서는 없는 경로가 한
> 번도 실행되지 않는다. Phase 7 의 교훈이 그대로 적용된다 — **손으로 우회한 배선은 검증되지
> 않는다.**

## 7. 화면

현황 `/` 의 "진행 중인 거래" 자리를 **두 열**로 바꾼다.

```
진행 중인 거래
┌─ 기록 ──────────────┬─ 거래소 ─────────────┐
│ 롱 0.01067 @ 59,500 │ 롱 0.01067 @ 59,500  │  ✓ 일치
└─────────────────────┴──────────────────────┘
                                    관측 2026-08-23 01:53 UTC
```

불일치는 **숨기지 않고 이름을 붙여 보여준다.**

| 경우 | 화면이 하는 말 |
|---|---|
| `RecordedOnly` | "기록에는 열려 있는데 거래소에 없다 — 청산을 적었는가?" |
| `ExchangeOnly` | "거래소에 포지션이 있는데 기록에 없다" |
| `QuantityDiffers` | "수량이 다르다 — 기록 0.01067 / 거래소 0.02134" |

**프론트는 숫자를 만들지 않는다**(`docs/adr/020`). 일치 여부 판정도 서버가 한다.

## 8. 하지 않는 것

- **주문을 내지 않는다.** 읽기 전용 키만 쓴다. `CLAUDE.md` 금지 항목이고 이 명세는 그것을
  바꾸지 않는다
- **불일치를 자동으로 고치지 않는다.** 기록을 거래소에 맞춰 자동 수정하면 "적기를 빠뜨렸다"
  는 사실 자체가 사라진다. 화면은 알려 주기만 하고 고치는 것은 사람이 기록 화면에서 한다
- **잔고 자동 입력은 이번 범위 밖.** `scope.md` 가 키의 가치로 적어 둔 둘 중 하나지만, 계획
  화면을 건드리는 별개의 변경이다
- **시크릿을 프론트에 보내지 않는다.** 브라우저는 우리 서버에만 요청한다

## 9. 완료 조건

1. `OPENAI_API_KEY` 도 바이낸스 키도 **없이** `.\gradlew.bat check` 통과 — **충족**
2. 키 없이 앱이 뜨고 다섯 화면이 동작한다. `/api/account/positions` 만 503 — **충족**
   (브라우저로 확인. 화면이 필요한 환경변수 이름까지 말한다)
3. `BinanceSigner` 가 바이낸스 공개 문서의 예제 벡터를 재현한다 — **충족**
4. 네 가지 `PositionMatch` 각각에 대해 테스트가 있다 — **충족**, 키도 DB 도 없이 돈다
5. 수량 0 인 응답이 포지션으로 잡히지 않는다 — **충족** (도메인과 어댑터 양쪽)
6. ArchUnit 규칙 4 가 `account.application → adapter` 를 막는다 — **충족**
   (위반 픽스처 `r4acc`. `r4a` 는 이미 `ai` 가 쓰고 있어 이름을 갈랐다)
7. 실제 키로 한 번 띄워 대조가 화면에 뜨는 것을 **브라우저로 확인** — **충족 (2026-08-23)**

> **실측에서 두 가지가 나왔다.**
>
> 하나는 위의 시계다. 키·권한·IP 는 전부 정상이었는데 요청이 전부 거절됐다 — 그 구분은
> 오류 코드를 직접 봐야만 됐다(`-1021` 이지 `-2015` 가 아니다).
>
> 다른 하나는 **이 기능이 첫 실행부터 실제 사례를 잡았다**는 것이다. 계좌에 `SHORT 0.114 @
> 76,955.23` 이 열려 있는데 기록에는 없었다 — `EXCHANGE_ONLY`. 앱 밖에서 연 포지션이고,
> 대조가 없었다면 현황 화면은 "진행 중인 거래가 없다" 라고만 말했을 것이다. **덮어쓰기가
> 아니라 대조를 고른 이유가 첫 화면에서 증명됐다.**
